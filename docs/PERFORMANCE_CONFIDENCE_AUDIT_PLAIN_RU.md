## Этап 1. Клиент: ощущение скорости при открытии экранов и чата

### 1. Настройки React Query по умолчанию

**По-простому:** Библиотека кэша данных по умолчанию считает ответы «вечно свежими» и не обновляет их при возврате на вкладку браузера.

**Сейчас:** В `queryClient` стоит «данные не устаревают сами» и отключён refetch при фокусе окна. Отдельные экраны (например список чатов) переопределяют это вручную.

**Предлагаем:** Осмысленные дефолты по типам данных: где нужна свежесть (списки, счётчики) — короткий «срок годности» или мягкое обновление в фоне; где редко меняется — оставить дольше. Чтобы везде было предсказуемо.

**Станет лучше:** Меньше ситуаций «на экране одно, на сервере уже другое» без видимой подгрузки. Пользователь либо видит актуальное, либо понимает, что идёт обновление.

---

### 2. Загрузка чата не через React Query

**По-простому:** История сообщений подгружается «вручную» через `fetch`, а не через общий кэш приложения.

**Сейчас:** Хук сам держит `loading`, ошибки и список сообщений. Ушёл из чата и вернулся — снова полный запрос к серверу.

**Предлагаем:** Один стиль с лентой и другими списками: кэш по `chatId`, дедупликация, фоновое обновление, отмена при уходе со страницы.

**Станет лучше:** Повторное открытие того же чата заметно быстрее; меньше лишней сети; проще делать «обновить в фоне» после реконнекта.

---

### 3. Несколько запросов подряд при открытии чата

**По-простому:** Сначала грузим карточку чата, потом папки, потом сообщения — как три очереди в магазине вместо одной кассы.

**Сейчас:** Для обычного чата: запрос чата → папки → сообщения; у группы иногда лишний повтор папок.

**Предлагаем:** Один запрос «всё для экрана чата» на сервере **или** хотя бы не ждать лишние шаги там, где можно параллелить.

**Станет лучше:** Меньше времени от тапа «открыть чат» до появления сообщений, особенно на мобильном интернете.

---

### 4. Запрет кэша браузера для чата

**По-простому:** Специально не кладём ответы API в общий кэш браузера — чтобы чужой не увидел чужие данные с того же компьютера.

**Сейчас:** И клиент, и сервер говорят «не кэшировать» для личных JSON.

**Предлагаем:** Оставить так для личных данных; для **публичных** картинок/видео по CDN — нормальные заголовки кэша отдельно.

**Станет лучше:** Безопасность не страдает; повторный просмотр одних и тех же **медиа** может стать быстрее за счёт CDN.

---

### 5. Долгий таймаут загрузки чата (15 секунд)

**По-простому:** До полутора десятков секунд экран может «висеть» в ожидании без ясной причины.

**Сейчас:** Таймаут 15 с до признания проблемы.

**Предлагаем:** Короче порог для показа «что-то не так» + кнопка «Повторить» + при наличии кэша показывать его сразу.

**Станет лучше:** Не сидишь перед пустым/скелетоном без конца; быстрее понимаешь, что сеть сбоила, и один тап исправляет.

---

### 6. Сразу 50 сообщений с сервера

**По-простому:** Первый пакет истории довольно толстый по размеру файла.

**Сейчас:** Запрашивается 50 сообщений за раз (сервер умеет и больше).

**Предлагаем:** Меньше первый кусок (например 20–30), остальное — при прокрутке вверх.

**Станет лучше:** Быстрее первый ответ и первый рендер; длинная история всё равно доступна чуть позже.

---

### 7. Спиннер при загрузке тяжёлой страницы

**По-простому:** Пока подгружается код новой страницы, виден только крутящийся индикатор.

**Сейчас:** `PageFallback` в `App.tsx` — спиннер по центру.

**Предлагаем:** Каркас будущего экрана (шапка, «рёбра» списка), как в крупных приложениях.

**Станет лучше:** Ощущение, что приложение «уже здесь», а не «зависло»; меньше тревоги в первые секунды.

---

### 8. Мгновенный офлайн только для чата по UUID

**По-простому:** Сохранённая копия из памяти телефона показывается сразу не во всех способах открыть чат.

**Сейчас:** Быстрый снимок из IndexedDB есть, если id — обычный UUID. Вход по короткой ссылке / public id может ждать сеть дольше.

**Предлагаем:** Там, где безопасно, хранить и подставлять снимок по тем же ключам, по которым открывают чат.

**Станет лучше:** Меньше «пустого» экрана при открытии из контактов и приглашений.

---

### 9. Огромный файл списка чатов

**По-простому:** Один файл на тысячи строк — тяжелее для браузера и для разработчиков.

**Сейчас:** `Chats.tsx` раздут.

**Предлагаем:** Разбить на логические части (список, шапка, модалки, логика подписок).

**Станет лучше:** Легче не сломать производительность новыми фичами; проще держать единые правила «загрузка / ошибка / пусто».

---

### 10. Плеер голосового: задержка и двойная загрузка при ошибке

**По-простому:** Пока файл не подгрузился, непонятно, идёт загрузка или сломалось; при сбое может пойти второй запрос.

**Сейчас:** Длительность появляется после метаданных; при ошибке — fallback через повторную загрузку в blob.

**Предлагаем:** Видимый «загружается» сразу; один понятный путь загрузки; не дублировать запрос без нужды.

**Станет лучше:** Голосовые ощущаются отзывчивее; меньше секунд ожидания на плохой сети.

---

### 11. Нет предзагрузки следующего голосового

**По-простому:** В цепочке автовоспроизведения каждый следующий файл начинает грузиться с нуля.

**Сейчас:** Есть задел в пропсах (`nextVoiceMessageId`), но без агрессивного prefetch.

**Предлагаем:** Лёгкая предзагрузка следующего сообщения (по возможности и лимитам трафика).

**Станет лучше:** Плавнее переход между голосовыми подряд, меньше пауз.

---

### 12. Весь список сообщений рисуется в DOM сразу

**По-простому:** Тысяча пузырей = тысяча узлов на экране — скролл и клавиатура могут лагать.

**Сейчас:** Виртуализации нет; мемоизация строк — ограниченно.

**Предлагаем:** Виртуальный список для длинных чатов + мемо у строки сообщения.

**Станет лучше:** Плавный скролл в старых переписках; меньше подтормаживаний при вводе.

---

### 13. Картинки в ленте без ленивой загрузки

**По-простому:** Браузер может пытаться тянуть все картинки сразу, даже далеко за пределами экрана.

**Сейчас:** Много `<img>` без `loading="lazy"` и `decoding="async"`.

**Предлагаем:** Системно включить ленивую загрузку и асинхронное декодирование для картинок ниже первого экрана.

**Станет лучше:** Быстрее первый показ ленты; меньше просадок FPS при скролле.

---

### 14. Поиск без кэша

**По-простому:** Ввёл запрос, ушёл, вернулся — сеть снова дергается за тем же текстом.

**Сейчас:** Ручной `fetch` в глобальном поиске.

**Предлагаем:** Обернуть в React Query с ключом по строке поиска и коротким временем жизни кэша.

**Станет лучше:** Повторный поиск того же — мгновенно из памяти; меньше нагрузки на сервер.

---

### 15. Незаметное фоновое обновление списка чатов

**По-простому:** Данные могут обновиться, а пользователь этого не видит.

**Сейчас:** Есть техническое различие «первая загрузка» и «фоновый refetch», но UI может быть слишком тихим.

**Предлагаем:** Лёгкий индикатор «обновляем…» в шапке или pull-to-refresh как эталон.

**Станет лучше:** Понятно, что список мог перестроиться; меньше ощущения «интерфейс сам прыгнул».

---

### 16. Тихие ошибки после восстановления сети

**По-простому:** После реконнекта сокета часть запросов может упасть без сообщения пользователю.

**Сейчас:** В некоторых ветках пустой `catch`.

**Предлагаем:** Лог + при необходимости тост «не удалось обновить, повторить».

**Станет лучше:** Не думаешь, что «всё синхронизировалось», когда на самом деле нет.

---

### 17. Тяжёлое переключение чата блокирует интерфейс

**По-простому:** Большой кусок React-дерева перерисовывается синхронно — кнопки могут на долю секунды «не жаться».

**Сейчас:** `useTransition` / отложенные обновления не используются для смены чата.

**Предлагаем:** Помечать смену треда как переход низкого приоритета, чтобы композер оставался отзывчивым.

**Станет лучше:** Меньше микролагов при переключении между диалогами.

---

### 18. Разные способы обновить данные после действий

**По-простому:** Список чатов и открытый диалог могут обновляться разными путями и разъехаться.

**Сейчас:** Где-то инвалидация кэша, где-то только локальный `setState`.

**Предлагаем:** Единые правила: после отправки/реакции/прочтения — согласованное обновление и списка, и треда.

**Станет лучше:** Совпадают последнее сообщение и счётчик непрочитанных; меньше «багов доверия».

## Этап 2. Сеть, API и сервер

### 1. Много запросов к БД на каждое «ответное» сообщение

**По-простому:** Для превью «ответ на…» сервер может ходить в базу отдельно на **каждое** сообщение в списке.

**Сейчас:** Цикл с `getMessage` на каждый `replyToId`.

**Предлагаем:** Один запрос: «дай все сообщения с этими id».

**Станет лучше:** Открытие чата с длинной перепиской и ответами — заметно быстрее; сервер меньше грузится.

---

### 2. Много подписей ссылок S3 на каждый список сообщений

**По-простому:** Каждое сообщение с файлом может требовать отдельной крипто-подписи URL на сервере.

**Сейчас:** До N операций presign на один ответ API.

**Предлагаем:** Пакетная подпись, кэш на миллисекунды в рамках запроса, или более долгоживущие подписи там, где безопасно.

**Станет лучше:** Быстрее отдаётся список сообщений с медиа; ниже CPU на VPS.

---

### 3. Сжатие ответов API в Node

**По-простому:** JSON можно сжимать gzip/brotli — меньше килобайт по проводу.

**Сейчас:** В коде Express не видно стандартного `compression` middleware (возможно делает nginx).

**Предлагаем:** Явно включить на одном уровне (Node **или** nginx) и проверить, что реально сжимается.

**Станет лучше:** Меньше времени загрузки ленты и больших списков на медленном интернете.

---

### 4. Личные ответы без кэша

**По-простому:** См. этап 1 п.4 — осознанное решение для приватности.

**Сейчас:** `Cache-Control: no-store` на приватные JSON.

**Предлагаем:** Не ослаблять для личных данных; публичное — отдельная политика.

**Станет лучше:** Безопасность сохраняется; ускорение только там, где оно не раскрывает чужие данные.

---

### 5. Первый экран сообщений можно сделать легче

**По-простому:** Сервер уже умеет отдать до 200 сообщений; клиент просит 50.

**Предлагаем:** Согласовать меньший первый запрос + курсор вверх (уже есть `before`).

**Станет лучше:** Быстрее «появились последние реплики»; история подгружается по мере скролла.

---

### 6. Один запрос вместо трёх при холодном открытии чата

**По-простому:** Объединить «кто в чате + папки + последние сообщения» в один ответ.

**Сейчас:** Три (и более) HTTP-запроса.

**Предлагаем:** Новый эндпоинт или расширение существующего с версией схемы.

**Станет лучше:** Резко меньше задержка на плохой сети; проще мобильный клиент.

---

### 7. Долгие запросы не всегда видны в логах по смыслу

**По-простому:** Есть `requestId`, но не везде по нему понятно, **какой** обработчик тормозил.

**Предлагаем:** В тяжёлых местах (список сообщений) логировать длительность с id запроса.

**Станет лучше:** Команда быстрее находит причину «у всех тормозит чат»; пользователь косвенно получает фиксы раньше.

---

### 8. Лента: лишние повторные запросы

**По-простому:** При некоторых сменах состояния React может инициировать повторную подгрузку первой страницы.

**Сейчас:** `fetchInfiniteQuery` с догрузкой первой страницы в `useEffect`.

**Предлагаем:** Проверить дубли в Strict Mode и зависимостях; оставить один осмысленный refetch.

**Станет лучше:** Меньше мигания и расхода трафика; стабильнее лента.

---

### 9. Ограничения размера тела запроса

**По-простому:** Большие файлы упираются в лимиты nginx и сервера.

**Сейчас:** В клиенте уже есть понятные тексты про `client_max_body_size`.

**Предлагаем:** Единая таблица лимитов в доке деплоя и одинаковые сообщения об ошибке.

**Станет лучше:** Пользователь сразу понимает «файл большой / настройка сервера», а не абстрактную ошибку.

---

### 10. AI-чат и обычный чат — разный UX ошибок

**По-простому:** Два похожих экрана ведут себя по-разному при сбое.

**Сейчас:** Разные хуки и тексты.

**Предлагаем:** Общий паттерн: ошибка + «Повторить» + скелетон.

**Станет лучше:** Меньше ощущения «тут всё серьёзно, тут как попало».

---

### 11. Защита от спама тяжёлыми GET

**По-простому:** Отправку сообщений уже лимитируют; список сообщений можно долбить без ограничений.

**Предлагаем:** Разумный rate limit на тяжёлые чтения с понятным ответом.

**Станет лучше:** Стабильность для всех при злоупотреблении или баге клиента; честное сообщение «подождите».

---

### 12. Индексы БД под листание истории

**По-простому:** Без индексов «дай 50 сообщений старше X» становится медленным на миллионах строк.

**Сейчас:** Есть курсор `beforeMessageId`; нужно подтвердить индексы под `(chat_id, created_at)` или аналог.

**Предлагаем:** Проверить план запроса в проде; добавить индекс при необходимости.

**Станет лучше:** Догрузка вверх не деградирует в больших группах.

---

### 13. Стикер-паки грузятся каждый раз заново

**По-простому:** Публичные данные можно кэшировать на клиенте дольше, чем личные.

**Сейчас:** API с `no-store`; клиент может не кэшировать агрессивно.

**Предлагаем:** Для публичных паков — `staleTime` в React Query минуты/часы.

**Станет лучше:** Быстрее открывается панель стикеров повторно.

---

### 14. Профилирование всего пути `listChatMessages`

**По-простому:** Нужно знать суммарное время: доступ, скрытые, реакции, presign.

**Сейчас:** Логика разнесена по шагам.

**Предлагаем:** Один тайминг в лог на запрос (dev/staging или sample в проде).

**Станет лучше:** Точечные оптимизации попадают туда, где реально боль.

---

### 15. Два запроса за реакциями

**По-простому:** «Все реакции» и «мои реакции» — два round-trip к БД.

**Предлагаем:** Объединить в один запрос с двумя наборами полей где возможно.

**Станет лучше:** Чуть быстрее каждый раз при открытии чата с реакциями.

---

### 16. Скрытые сообщения

**По-простому:** Список id скрытых для пользователя грузится на каждый список сообщений.

**Сейчас:** Отдельный запрос в цепочке.

**Предлагаем:** Если внутри одного HTTP вызова дубли — кэш на время обработки.

**Станет лучше:** Микроускорение на очень тяжёлых путях.

---

### 17. Тяжёлые фоновые задачи и основной чат на одном процессе

**По-простому:** Парсер, EDGE, админка могут конкурировать за CPU с открытием чата.

**Сейчас:** Монолитный процесс Node.

**Предлагаем:** Очереди, отдельные воркеры, лимиты на долгие задачи.

**Станет лучше:** Пики фоновой работы не делают «всем лагает мессенджер».

---

### 18. Целевые показатели (SLO) и метрики

**По-простому:** Без цифр «быстро» — субъективно.

**Предлагаем:** Зафиксировать, например: p95 открытия чата < X с; публикация поста < Y с.

**Станет лучше:** Решения по оптимизации приоритизируются; регрессии видны до пользователей.

---

## Этап 3. Realtime и WebSocket

### 1. Один сокет на пользователя

**По-простому:** Два WebSocket = двойная нагрузка и гонки «кто главный».

**Сейчас:** Архитектура стремится к одному соединению; в коде есть защита от параллельного открытия.

**Предлагаем:** Сохранять инвариант при любых новых фичах.

**Станет лучше:** Меньше странных багов «сообщение пришло дважды» / «пропало».

---

### 2. Подписки на чаты после переподключения

**По-простому:** После обрыва связи клиент снова шлёт список «на какие чаты подписан».

**Сейчас:** При `onopen` перечисляются все `chatId` из Map.

**Предлагаем:** При смене чата гарантированно снимать подписки, которые больше не нужны.

**Станет лучше:** Меньше лишнего трафика и утечек памяти на долгой сессии.

---

### 3. Новое соединение вытеснило старое

**По-простому:** Два устройства или вкладки — сервер может закрыть старый сокет специальным кодом.

**Сейчас:** Не делается агрессивный reconnect в этом случае — чтобы не было пинг-понга.

**Предлагаем:** Оставить логику; описать для поддержки и пользователей.

**Станет лучше:** Меньше бесконечных переподключений; предсказуемое поведение «где открыт последний — там живой сокет».

---

### 4. Огромный файл серверного WebSocket

**По-простому:** Звонки и чат в одном месте — сложно менять без регрессий.

**Сейчас:** `server/calls/ws.ts` очень большой.

**Предлагаем:** Разнести по модулям с чёткими границами (чат / звонки / метрики).

**Станет лучше:** Быстрее и безопаснее развитие; меньше поломок при правках.

---

### 5. Прочитано и подписка на тред

**По-простому:** Событие «прочитал» может прийти до того, как сервер зарегистрировал открытый чат.

**Сейчас:** Есть очередь `pendingChatRead` и сброс при subscribe.

**Предлагаем:** Покрыть автотестом сценарий гонки.

**Станет лучше:** Не «залипают» галочки и счётчики непрочитанного.

---

### 6. Обновление после реконнекта только на видимой вкладке

**По-простому:** Не тратим сеть, когда вкладка в фоне.

**Сейчас:** Refetch хвоста при `visibilityState === visible`.

**Предлагаем:** При возврате на вкладку показывать лёгкий индикатор «подтягиваем новое».

**Станет лучше:** Пользователь понимает, почему сообщения «догрузились» через секунду.

---

### 7. Метрики доставки сообщений в чат

**По-простому:** Для звонков метрики есть; для чата — расширить.

**Предлагаем:** Задержка от записи в БД до события в WS (выборочно).

**Станет лучше:** Видно, «тормозит сервер» или «сеть у клиента».

---

### 8. Согласованность списка чатов и треда

**По-простому:** Реакции и правки приходят в открытый чат по WS; список слева должен обновляться тем же событием или инвалидацией.

**Предлагаем:** Проверить все типы событий (`notifyChatListUpdate` и т.д.).

**Станет лучше:** Нет рассинхрона превью и открытого диалога.

---

### 9. Heartbeat и мобильный фон

**По-простому:** ОС убивает фоновые сокеты; нужны разумные таймауты и быстрый reconnect.

**Предлагаем:** Ревизия ping/pong и таймаутов под iOS/Android WebView.

**Станет лучше:** Меньше «час не было сети» в приложении при реальном интернете.

---

### 10. Очередь исходящих сообщений в сокет

**По-простому:** Пока сокет закрыт, пакеты копятся в очереди.

**Сейчас:** Есть `outgoingQueue`.

**Предлагаем:** Если очередь длинная — показать в UI «ожидает соединения».

**Станет лучше:** Понятно, почему «не отправилось» секунду-другую.

---

### 11. Подписка на удаление сообщений

**По-простому:** Отдельный канал уведомлений; при уходе из чата подписка должна сниматься.

**Предлагаем:** Аудит cleanup в `useEffect` при смене `chatId`.

**Станет лучше:** Нет лишних обработчиков и утечек.

---

### 12. Индикаторы «печатает» / «записывает голос»

**По-простому:** Нужен throttle на клиенте и лимит на сервере.

**Предлагаем:** Сохранить баланс нагрузка / отзывчивость.

**Станет лучше:** Стабильный сервер и батарея; индикатор всё ещё живой.

---

### 13. Отметка прочитанным только для открытого чата

**По-простому:** Иначе можно пометить прочитанным то, что пользователь не открывал.

**Сейчас:** `threadOpenChatIdsRef` на клиенте и логика на сервере.

**Предлагаем:** Не ослаблять; тесты на регрессию.

**Станет лучше:** Корректные галочки и приватность.

---

### 14. Приоритет трафика звонка и чата

**По-простому:** Один канал несёт и сигналинг звонка, и чат.

**Предлагаем:** Не блокировать критичный сигналинг большими чат-пакетами (приоритеты/очереди).

**Станет лучше:** Меньше артефактов «звонок лагает, пока активен чат».

---

### 15. Актуальность документации по звонкам и WS

**По-простому:** Код уехал вперёд — доки врут.

**Предлагаем:** Регулярно сверять `CALLS_RELIABILITY.md` и план улучшений с кодом.

**Станет лучше:** Меньше ошибок при разработке = стабильнее продукт.

---

### 16. Тест: обрыв сети во время отправки

**По-простому:** Сообщение должно уйти из outbox после восстановления.

**Предлагаем:** Автотест или чеклист перед релизом.

**Станет лучше:** Не теряется доверие к «отправлено».

---

### 17. Логи причины закрытия сокета на клиенте

**По-простому:** Уже логируется локально; в проде полезны агрегированные причины.

**Предлагаем:** Опционально breadcrumbs в систему мониторинга (с учётом privacy).

**Станет лучше:** Массовые обрывы диагностируются без «у нас всё ок».

---

### 18. Версия протокола WebSocket

**По-простому:** После обновления сервера старая вкладка может говорить на старом языке.

**Предлагаем:** Явная версия в handshake; при несовпадении — понятное сообщение / обновление приложения.

**Станет лучше:** Нет молчаливого «ничего не работает».

---

## Этап 4. Медиа: голос, кружки, лента

### 1. Первый тап по видеокружку

**По-простому:** Видео не грузится, пока не нажали — экономия трафика, но первый тап может казаться «пустым».

**Сейчас:** `src` у `<video>` только после активации.

**Предлагаем:** Мини-спиннер или пульс внутри круга на первом тапе.

**Станет лучше:** Понятно, что идёт загрузка, а не «сломалось».

---

### 2. Предзагрузка следующего кружка

**По-простому:** Следующее видео в чате можно начать подгружать, когда текущее почти в зоне видимости.

**Предлагаем:** IntersectionObserver + лёгкий prefetch метаданных.

**Станет лучше:** Быстрее старт при листании кружков в длинном чате.

---

### 3. Постер видеокружка с сервера

**По-простому:** Превью-картинка должна приходить быстро вместе с ответом загрузки.

**Сейчас:** В API уже заложен `posterUrl`.

**Предлагаем:** Профилировать генерацию на сервере; не блокировать ответ.

**Станет лучше:** В ленте сообщений кружок выглядит цельным сразу после отправки.

---

### 4. Подписи URL для медиа

**По-простому:** См. этап 2 п.2 — много подписей = медленный список.

**Предлагаем:** Пакеты, TTL, CDN с ограничением пути.

**Станет лучше:** Быстрее открывается чат с кучей вложений.

---

### 5. Офлайн-кэш голосовых

**По-простому:** Уже кэшируется — хорошо.

**Предлагаем:** Лимиты размера и политика очистки, чтобы не забить хранилище.

**Станет лучше:** Реже «внезапно не играет» из-за переполнения.

---

### 6. Автовоспроизведение в ленте

**По-простому:** Много одновременных видео = жарко и лагает.

**Предлагаем:** Лимит активных плееров + уважение `prefers-reduced-motion`.

**Станет лучше:** Плавный скролл; доступность; батарея.

---

### 7. Картинки в постах

**По-простому:** Ленивая загрузка и async decode.

**Предлагаем:** Системно в компонентах ленты и профиля.

**Станет лучше:** Быстрее первый экран; меньше скачков вёрстки при подгрузке (если задать размеры).

---

### 8. Сториз и соседние слайды

**По-простому:** Предзагрузка текущего ±1 как в Reels.

**Предлагаем:** Выровнять поведение между сториз и reels-лентой.

**Станет лучше:** Меньше белых кадров между историями.

---

### 9. Очередь транскода сториз

**По-простому:** Долгая обработка = долго «висит» публикация.

**Предлагаем:** Мониторинг очереди; UX «обрабатывается» с плейсхолдером в ленте.

**Станет лучше:** Понятно, что пост не потерян, а в работе.

---

### 10. Один формат записи голоса

**По-простому:** Разные браузеры дают разные контейнеры — больше fallback.

**Предлагаем:** Свести к предсказуемому формату/битрейту на клиенте и приём на сервере.

**Станет лучше:** Меньше «у меня не играет» на Safari/Android.

---

### 11. PDF и файлы

**По-простому:** Не качать весь файл для превью в списке.

**Предлагаем:** Ленивая загрузка до тапа.

**Станет лучше:** Экономия трафика и памяти в длинных чатах.

---

### 12. Водяной знак на картинках постов

**По-простому:** Если обработка синхронная — пользователь ждёт перед появлением в ленте.

**Предлагаем:** Сначала показать оригинал/промежуточный вариант, водяной знак — асинхронно.

**Станет лучше:** Ощущение «выложил — сразу вижу».

---

### 13. Единая обработка ошибок медиа

**По-простому:** Одинаковая иконка «повторить» на голосе и кружке.

**Предлагаем:** Общий маленький компонент / хук.

**Станет лучше:** Понятно, что делать при сбое.

---

### 14. Веб vs приложение Capacitor

**По-простому:** Разные базовые URL и CORS для медиа.

**Сейчас:** В `api-base` уже есть логика для натива.

**Предлагаем:** Чеклист перед релизом билдов на реальные URL S3.

**Станет лучше:** Нет класса багов «на сайте ок, в приложении картинки не грузятся».

---

### 15. Большие видеокружки на мобильном интернете

**По-простому:** 500 МБ на LTE — больно и неожиданно.

**Предлагаем:** Предупреждение «большой файл, мобильная сеть» до старта upload.

**Станет лучше:** Пользователь сам решает; меньше злости на счёт трафика.

---

### 16. Два UI кружка (Pulse и обычный)

**По-простому:** Разное поведение превью и ошибок.

**Предлагаем:** Синхронизировать preload и ошибки.

**Станет лучше:** Единое ощущение качества в разных шаблонах чата.

---

### 17. Кэш CDN для публичных медиа

**По-простому:** Повторный просмотр не должен идти на origin каждый раз.

**Предлагаем:** Настроить `Cache-Control` на bucket/CDN для публичных объектов.

**Станет лучше:** Повторные просмотры и шаринг быстрее.

---

### 18. Доступность (screen reader)

**По-простому:** Голос и кружок должны иметь понятные подписи.

**Предлагаем:** Пройтись по `aria-label` системно.

**Станет лучше:** Продукт пригоднее для людей с ограничениями; выше общее качество.

---
