# Аудит производительности и «уверенности» UX

**Дорожная карта «опережающих» ставок и волн внедрения** (не про модный стек, а про инварианты и горизонт 1–2+ года): [`PERFORMANCE_CONFIDENCE_FORWARD_ROADMAP.md`](./PERFORMANCE_CONFIDENCE_FORWARD_ROADMAP.md).

**Тот же аудит «на пальцах»** (сейчас / предлагаем / что станет лучше по каждому пункту): [`PERFORMANCE_CONFIDENCE_AUDIT_PLAIN_RU.md`](./PERFORMANCE_CONFIDENCE_AUDIT_PLAIN_RU.md).

**Ручная приёмка после правок:** [`PERFORMANCE_QA_CHECKLIST.md`](./PERFORMANCE_QA_CHECKLIST.md).

Документ фиксирует пятиступенчатый аудит: воспринимаемая скорость, сеть/API, realtime, медиа, архитектура. У каждого пункта: обоснование, затронутые файлы/модули, оценка риска регрессии при внедрении.

**Легенда риска:** низкий — локальная правка или флаг; средний — меняется контракт данных или несколько слоёв; высокий — ядро чата/WS/оплата стабильности.

## Этап 1. Клиент: воспринимаемая скорость и уверенность при загрузке

| # | Находка и рекомендация | Почему это важно | Файлы / модули | Риск |
|---|------------------------|------------------|----------------|------|
| 1 | **Глобальный `staleTime: Infinity` и `refetchOnWindowFocus: false` в React Query** — данные не «устаревают» сами; свежесть только от инвалидаций. | В топ-мессенджерах при возврате в приложение часто есть мягкое обновление списков. | 2 | **`useChatMessages` без React Query** — ручные `apiFetch`, локальный `loading`/`error`. | Повторный вход в тот же чат снова бьёт в сеть; нет дедупликации параллельных запросов; сложнее унифицировать retry и фоновое обновление как в TG/IG. | `client/src/features/chat/hooks/useChatMessages.ts`, `client/src/pages/ChatDetail.tsx`, `docs/CHAT_DETAIL_RULES.md` | высокий |
| 3 | **Водопад запросов при открытии UUID-чата:** `GET /chats/:id` + `GET folders` + `GET messages` (у группы возможен повторный `folders`). | Каждый RTT добавляется последовательно; TTI хуже, чем у одного агрегированного ответа или хотя бы параллельного `messages` с известным `chatId` после первого ответа. | `useChatMessages.ts`, `server/chats/register-chats-routes-read.ts`, `server/messages/routes.ts` | средний |
| 4 | **`cache: "no-store"` на клиентских запросах чата** вместе с серверным `Cache-Control: no-store`. | Осознанно для приватности; минус — нет даже кратковременного HTTP-кэша. | 5 | **`CHAT_LOAD_TIMEOUT_MS = 15000`** — до 15 с ожидания до явной ошибки. | Долгий «подвисший» скелетон без прогресса снижает доверие сильнее, чем быстрый таймаут + «Повторить» + фоновая догрузка. | `client/src/features/chat/constants.ts`, `useChatMessages.ts` | низкий |
| 6 | **`MESSAGES_PAGE = 50`** при первом заходе. | Большой JSON на медленной сети; в эталонах часто меньший первый экран + догрузка. Сервер уже допускает до 200 — клиент выбирает 50. | `constants.ts`, `server/messages/routes.ts` (`parsePositiveIntQuery`) | низкий |
| 7 | **Lazy-маршруты + `PageFallback` — только спиннер.** | IG/TG показывают каркас экрана (шапка/список-скелетон), а не пустой спиннер — выше ощущение скорости. | `client/src/App.tsx` | низкий |
| 8 | **Офлайн-снимок из IndexedDB только для UUID-чата.** | Открытие по public id / invite code не получает мгновенного снимка — дольше пустота/скелетон. | `useChatMessages.ts`, `client/src/lib/chat-offline-store.ts` | средний |
| 9 | **`Chats.tsx` — монолит тысяч строк.** | Тяжелее парсинг/инициализация при первом заходе на вкладку; сложнее гарантировать единый паттерн loading/background sync. | `client/src/pages/Chats.tsx` | средний |
| 10 | **`VoiceMessagePlayer`:** до `loadedmetadata` длительность и «готовность» неочевидны; при ошибке — полный `apiFetch` + blob fallback (двойная задержка). | Голосовые в TG ощущаются «сразу кликабельными»; нужен явный skeleton/индикатор загрузки и устранение дублирующего fetch при известной причине ошибки. | `client/src/components/VoiceMessagePlayer.tsx`, `ChatMessageRow.tsx` | средний |
| 11 | **Нет префетча следующего голосового в цепочке** (`nextVoiceMessageId` есть в пропсах ряда). | Автоплей по цепочке может ждать холодный старт каждого файла. | `ChatMessageRow.tsx`, возможно `useChatMessages.ts` | низкий |
| 12 | **Список сообщений без виртуализации и без мемо-пузыря** (см. `OPTIMIZATIONS.md`). | Длинные треды → лаг скролла и ввода; ощущение «тяжёлого» приложения. | `client/src/pages/ChatDetail.tsx`, компоненты списка | средний |
| 13 | **Изображения в ленте/чате часто без `loading="lazy"` / `decoding="async"`** (частично уже есть у видеокружка poster). | Конкурирующая загрузка декодирования блокирует main thread; лента «подтупливает». | `PostMedia.tsx`, `ChatMessageRow.tsx`, профиль | низкий |
| 14 | **`GlobalSearch` на ручном fetch** — нет кэша по запросу, нет дедупликации. | Повторный ввод того же запроса снова бьёт в API; ощущение медлительности. | `client/src/components/GlobalSearch.tsx` | низкий |

| 16 | **После реконнекта WS** — `refetchLatestMessagesTail` и обновление чата; пустые `.catch(() => {})` на части путей. | Тихий провал не даёт тоста — пользователь думает, что «всё синхронизировано». | `useChatMessages.ts` | средний |
| 17 | **React 19: не используются `useTransition` / `useDeferredValue`** для тяжёлого переключения чата/вкладок. | Крупный commit при смене `chatId` может блокировать отзывчивость композера. | `ChatDetail.tsx`, `Chats.tsx` | низкий |
| 18 | **Единый контракт инвалидации** после мутаций (чаты, сообщения) — разрозненные `invalidateQueries` vs ручной `setState` в чате. | Риск рассинхрона списка чатов и треда; пользователь видит разные unread/последние сообщения. | Хуки чата, `useSendMessage.ts`, `Chats.tsx` | высокий |

| 10 | **AI-чат и обычный чат** — разные пути; для AI нет того же offline-first — приемлемо, но единый паттерн ошибок/повтора. | Снижение когнитивного шума между экранами. | `client/src/features/chat/hooks/useAiChat.ts` | низкий |

## Краткое резюме

- **Самый большой выигрыш в ощущении скорости:** уменьшить водопад запросов при открытии чата (серверный aggregate или параллель + меньший первый page), убрать N+1/presign шторм на `listChatMessages`, перевести чат на кэшируемую модель данных (React Query / SWR) с явными состояниями фона.
- **Самый большой выигрыш в «уверенности»:** скелетоны/каркасы вместо голого спиннера, явные индикаторы синхронизации и ошибок без тихих `catch`, стабильный WS + догрузка хвоста после реконнекта.
