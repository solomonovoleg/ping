# API: авторизация, токены, публичные ручки, PATCH/PUT

Один документ для разработчиков и аудита: **где живут секреты**, **как сервер выбирает пользователя**, **что вообще можно вызывать без входа**, **почему смешаны PATCH и PUT**.

---

## 1. Как клиент доказывает личность

| Механизм | Где задаётся | Где проверяется |
|----------|----------------|-----------------|
| **Сессия** | Cookie `ping.sid` (express-session), `httpOnly`, срок ~30 дней | `server/auth/session.ts` → `req.session.userId` |
| **Bearer** | Заголовок `Authorization: Bearer <token>` | Тот же модуль: `req.authUserId` через `getUserIdByToken` |

**Итоговый пользователь запроса** (`getUserId`):

```text
req.session?.userId ?? req.authUserId
```

Сначала сессия (если в запросе есть валидная кука), иначе — Bearer. Оба канала могут прийти в одном запросе (веб часто: кука + `apiFetch` добавляет Bearer из хранилища).

---

## 2. Что такое Bearer `pm....`

- Реализация: `server/auth/token.ts` (префикс `pm.`, HMAC, TTL ~30 суток).
- Выдаётся при логине вместе с установкой сессии (см. `server/auth/routes.ts`).
- **Не хранится в БД построчно** — проверка по подписи и сроку.

---

## 3. Где на клиенте лежит токен (и почему его «находят»)

| Хранилище | Кто читает | Риск |
|-----------|------------|------|
| `localStorage`, ключ `ping_auth_token` | Любой JS на **том же origin** | При XSS токен проще украсть, чем `HttpOnly`-куку |
| Capacitor **Preferences** | нативное приложение | Утечка через компрометацию устройства / бэкапа |
| Cookie `ping.sid` | Браузер сам шлёт на наш домен; **не** доступна из `document.cookie` | Видна в DevTools, Postman, экспорте `curl`, расширениях, малвари |

**Почему токен «утёк» у конкретного человека** — почти всегда: скопировали запрос из DevTools, Postman, вирус, расширение, чужой ПК, фишинг, утечка лога. Это не «норма», это компрометация секрета.

Клиентский слой: `client/src/lib/api-base.ts` (`apiFetch`, `setAuthToken`, `getAuthHeaders`).

---

## 4. PATCH и PUT — зачем оба

В проекте **не ошибка**, а **разная семантика**:

| Метод | Смысл в нашем API | Примеры |
|-------|-------------------|---------|
| **PATCH** | Частичное изменение ресурса (только переданные поля) | `/api/users/me`, `/api/posts/:postId`, `/api/chats/:id`, правка текста сообщения, папки чата, треки, сториз archive |
| **PUT** | Подмена/фиксация состояния целого смыслового блока (исторически так сложилось) | `/api/chats/:id/read` (прочитано), `/api/chats/:chatId/translate-prefs`, `/api/chats/:chatId/vibe/override` |

**Правило для новых ручек:** по возможности **PATCH** для «обнови пару полей»; **PUT** — если по смыслу «положи новое состояние целиком» (или явно документируй в этом файле).

## 5. Публичные и полупубличные эндпоинты

Ниже — то, что **не требует** `requireAuth` или отвечает без 401 для анонима. Всё остальное под `/api/...` с `requireAuth` / админ-гейтами — **личные данные только для вошедшего**.

**Явно без входа (или осмысленный пустой ответ):**

- `GET /api/build-info` — версия сборки (для деплоя/поддержки).
- `GET /api/time` — время сервера.
- `GET /api/platform/announcement` — публичный текст объявления.
- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`.
- `GET /api/auth/me` — без сессии отдаёт `{}`, не 401 (чтобы не засорять консоль на лендинге).

**Данные с ограничениями (проверки в сервисе):**

- `GET /api/posts/:postId` — видимость поста (`public` / подписчики / черновик), см. `assertPostReadableByViewer`.
- `GET /api/posts/:postId/comments` — только если пост доступен зрителю.
- `GET /api/users/:userId/stories` — сториз автора (как публичное кольцо); без входа `viewerId` пустой.

**Публично с rate limit:**

- `GET /api/referrals/check` — проверка рефкода (имя пригласившего и срок).

**Админка** (`/api/admin/...`) — отдельный слой: после `requireAdmin` / ролей, не смешивать с пользовательским трафиком.

Если добавляешь **новую** публичную ручку с данными — обязательно: ревью на утечки PII, при необходимости **rate limit** (`server/auth/rate-limit.ts` или `api-shield`), не логировать `Authorization` в access-логах.

## 6. Чеклист безопасности для нового API

1. Нужен ли доступ без авторизации? Если нет — сразу `requireAuth` (или админ-гейт).
2. Любой идентификатор в URL проверяется на **членство / видимость** в сервисе, а не только в роуте.
3. Ответы с персональными данными — заголовки `Cache-Control: no-store, private` где уместно (см. `server/middleware/no-store-private-json.ts` для чатов).
4. Не класть секреты в URL query (попадут в Referer и логи прокси).
5. Понимать разницу: **HttpOnly cookie** vs **Bearer в localStorage** при оценке XSS.

## Отладка: «после правок безопасности чаты не открываются»

1. **`dm-by-public-id` → 429** — сработал лимит перебора (см. `dmByPublicIdLimiter` в `server/auth/rate-limit.ts`). Подождать ~1 мин или поднять лимит.
2. **`getOrCreateDmChat`** — поиск и создание лички на PostgreSQL идёт через **один `pg`‑клиент** (`BEGIN` / `COMMIT`), без сырого `drizzle.execute` внутри транзакции, чтобы не зависеть от формата ответа драйвера.
3. Логи PM2 на сервере: `pm2 logs <имя_процесса>` — искать `Error`, `ROLLBACK`, `chats`.
