# План: микросервис EDGE в репозитории

**Продукт (типы контента, персонаж, задания, призы, лидерборд):** см. **`docs/EDGE_PRODUCT_SPEC.md`**.

**Контекст:** план опирается на текущую платформу (`posts.edge_id`, `client/src/pages/EdgeCompanion.tsx`, `client/src/lib/edge-gamification.ts`, заглушки в `server/edge/routes.ts`).

**Цель:** папка **`EDGE/`** — отдельный Node/Express-процесс, **своя БД**, свои **роутеры**; файлы **≤ 200 строк**; логика по **подпапкам на домен** (одна зона ответственности — одна папка).

**Связь с платформой:** платформа остаётся источником постов и `edge_id`; EDGE хранит **данные кампаний, персонажа и прогресса** и отдаёт свой API.

---

## Этап 0 — Принятые решения (обновлено)

### БД

- **Один кластер PostgreSQL** (как у основного приложения), логически **отдельно от core**: отдельная **база** `ping_moot_edge` *или* схема `edge` в той же БД — без внешних ключей на таблицы платформы.
- Связь с пользователем платформы только **opaque id**: `platform_user_id` (UUID/число строкой), который передаёт прокси после проверки сессии/JWT на платформе.

### Независимость и локализация (обязательные правила)

1. **Отдельный процесс** (PM2 `edge`), **отдельный пул подключений** к БД — падение EDGE **не** валит Node-процесс `ping-moot`.
2. **Платформа не импортирует** код из `EDGE/` — только тонкий слой `server/edge/routes.ts` (HTTP-клиент + таймаут).
3. **Клиент** в проде бьёт в **тот же origin**, что и API: `GET /api/edge/...` на домене приложения → **прокси на localhost:EDGE_PORT** с **коротким таймаутом** (например 2–3 с). При таймауте/502/ECONNREFUSED или если upstream не настроен — платформа отдаёт **503 JSON** (`edge_*`) **только для edge-ручек**, без фейковых тел ответов.
4. Старт и health-check **основного** приложения **не зависят** от доступности EDGE.
5. Ошибки EDGE **логируются** на платформе, без проброса исключений в общий middleware чата/постов.

*Итог:* микросервис **максимально локализован**; «не рушит» основной сервис при сбоях, если соблюдать прокси+таймаут+fallback.

### Как «вызывается» (рекомендация)

| Слой | Кто куда ходит |
|------|----------------|
| Браузер / приложение | Только `https://<домен>/api/edge/...` (как сейчас `fetchEdgeCompanionCampaignConfig`). |
| Платформа | Внутренний `EDGE_URL` (например `http://127.0.0.1:3092`) + заголовок `Authorization: Bearer <EDGE_SERVICE_SECRET>` (или `X-Edge-Secret`). |
| EDGE | Не ходит в БД платформы; доверяет заголовку/подписи, которую выставляет только прокси. |

Прямой вызов клиента на отдельный поддомен EDGE **не обязателен** и усложняет CORS/токены — при желании можно добавить позже.

### Референс UI: «Птенец-помощник»

Скрин из продукта задаёт домены данных и API (всё живёт в EDGE, не в core):

| Элемент UI | Смысл для EDGE |
|------------|----------------|
| Возраст, уровень, полоса «7д» | Состояние прогресса + расчёт от `created_at` / правил кампании. |
| «Голоден», таймер «Разозлится через…» | Производные поля + **время последней кормёжки** / дедлайны в БД или расчёт на чтение. |
| «Покормить» | `POST` действие (идемпотентно по request-id при необходимости). |
| «Каталог» | Отдельный подмодуль предметов/скинов (таблицы + `GET` списка). |
| Реплика «Нужна помощь», вкусы | Состояние + опционально JSON предпочтений пользователя в EDGE. |

В коде — отдельные подпапки, например `pet/` (состояние птенца, кормление, таймеры) и `catalog/` рядом с `companion/campaign-config`.

## Ограничения качества

- Ошибки API: осмысленные коды 4xx/5xx и тело JSON `{ error, message? }`.
- Валидация входа: `zod` в тонких слоях (отдельные файлы ≤200 строк).
- Без «божественных» файлов: роутер только маршруты, логика в `service.ts`.
