# Технический аудит: чаты не загружаются, сообщения не отправляются, профили недоступны

Дата: 2025-03-18. Цель: выявить **все возможные причины** трёх проблем и дать рекомендации по исправлению.

---

## 1. Чаты не загружаются

### Цепочка на клиенте

- **Страница:** `client/src/pages/Chats.tsx`
- **Запрос:** `GET /api/chats` через `fetchChats()` → `apiFetch(\`${API}/chats\`, { cache: "no-store" })`
- **Состояния:** `isLoading`, `isError`, `refetch` из `useQuery({ queryKey: ["chats"], queryFn: fetchChats })`
- **Ошибка:** при `!res.ok` в `fetchChats()` выбрасывается `throw new Error("Не удалось загрузить чаты")` → React Query помечает `isError`, показывается `ErrorWithRetry` с кнопкой «Повторить»

### Возможные причины (полный список)

| № | Причина | Где проявляется | Как проверить / исправить |
|---|--------|------------------|----------------------------|
| 1 | **401 Unauthorized** — нет сессии или токена | `requireAuth` на сервере возвращает 401 | В вебе: куки не отправляются (другой домен без credentials / CORS / SameSite). В нативе: не передан Bearer (после логина не вызван `setAuthToken(data.token)` или ответ без `token`) |
| 2 | **Сеть недоступна** — таймаут, DNS, нет интернета | Запрос не завершается или падает с ошибкой сети | Проверить `navigator.onLine`, логи сети в DevTools, на устройстве — интернет и файрвол |
| 3 | **Неверный базовый URL API** | В нативе `API_BASE` пустой или не тот хост | Задать `VITE_API_URL` при сборке (например `https://pingos.ru`). Без него запросы идут на относительный путь — в нативе это может быть не тот сервер |
| 4 | **CORS** — сервер не отдаёт нужные заголовки для origin клиента | Браузер блокирует ответ (в консоли CORS error) | Настроить CORS на сервере (credentials: true, нужный Origin). Для натива с отдельным доменом API — тот же домен в allowed origins |
| 5 | **Ошибка/падение на сервере при обработке GET /api/chats** | 500 или необработанное исключение | Логи сервера. В роуте: `storage.getChatsForUser(userId)` или цикл по чатам (getLastMessage, getChatMemberIds, getUser и т.д.) могут бросить (БД, память) |
| 6 | **Нет DATABASE_URL / БД недоступна** | При использовании `DbStorage`: ошибка подключения или запроса | На сервере проверить `DATABASE_URL`, доступность PostgreSQL. При падении БД сервер может вернуть 500 или таймаут |
| 7 | **Сессия не сохраняется (веб)** | После входа кука не ставится или не уходит обратно | Проверить: `SESSION_SECRET`, `SESSION_SAME_SITE` (при cross-origin нужен `none` и HTTPS), `proxy: true` за nginx, кука `ping.sid` в Application → Cookies |
| 8 | **Регистрация без передачи token в натив** | В нативе после логина в ответе есть `token`, но клиент не вызывает `setUserFromLogin` с этим токеном | Убедиться, что после успешного login/register вызывается `setUserFromLogin(data)` и в `data` есть `token` |
| 9 | **Пустой список при успешном 200** | Чаты загружаются, но массив пустой | Это не «не загружаются», а «нет чатов». Проверить: у пользователя есть записи в `chat_members` для этого `userId` (БД) |

### Серверная цепочка (для отладки)

- `server/chats/routes.ts`: `GET /api/chats` → `requireAuth` → `getUserId(req)` → `storage.getChatsForUser(userId)`.
- `getUserId`: `req.session?.userId ?? req.authUserId`. В нативе `authUserId` ставится из заголовка `Authorization: Bearer <token>` (middleware в `session.ts`).
- Если сессия/токен не валидны → 401 до вызова storage.

## 2. Сообщения не отправляются

### Цепочка на клиенте

- **Отправка текста:** `client/src/features/chat/hooks/useSendMessage.ts` → `handleSend` → `apiFetch(\`${API}/chats/${chatId}/messages\`, { method: "POST", body: JSON.stringify({ content, replyToId }) })`
- **Условия раннего выхода:** `if (!text || !user || sending) return;` — пустой текст, нет текущего пользователя или уже идёт отправка.

### Возможные причины (полный список)

| № | Причина | Где проявляется | Как проверить / исправить |
|---|--------|------------------|----------------------------|
| 1 | **401 Unauthorized** | Та же логика, что и для чатов: сессия/токен не переданы или невалидны | См. раздел про чаты (куки, Bearer, CORS, SESSION_*) |
| 2 | **400 Bad Request — "content required"** | Сервер требует непустое строковое `content` | На клиенте уже есть проверка `message.trim()`, но если body не долетит или будет пустой/не JSON — сервер вернёт 400. Проверить Network: тело запроса |
| 3 | **Сеть / таймаут** | Запрос не завершается, fetch бросает | То же, что п.2–3 раздела про чаты. На клиенте при первой неудаче тост не показывается — только статус «failed» у сообщения; тост только при «Повторить» |
| 4 | **Неверный или пустой chatId** | POST уходит с пустым или несуществующим chatId | Если чат открыт по publicId, сначала вызывается `dm-by-public-id`, затем `resolvedChatId` ставится в uuid чата. До этого момента отправка идёт с пустым chatId (хук может не дать отправить, если chatId пустой — проверить передачу `chatId` в useSendMessage) |
| 5 | **user === null** | После истечения сессии или до загрузки /me | `handleSend` выходит по `if (!user)`. Проверить AuthContext и то, что на экране чата user не сбросился |
| 6 | **Серверная ошибка при createMessage** | 500 от сервера | Логи сервера. Возможны: ошибка БД (constraint, недоступность), исключение в `storage.createMessage` или после (notifyNewMessage, getChatMemberIds и т.д.) |
| 7 | **Ошибка при пересылке** | 403 "Нет доступа к пересылаемому сообщению" или 404 "Пересылаемое сообщение не найдено" | Проверить, что `originalChatId` и `forwardedFromMessageId` принадлежат чату, к которому у пользователя есть доступ |
| 8 | **Клиент не показывает текст ошибки при первой отправке** | При `!res.ok` сообщение помечается «failed», текст восстанавливается в поле, но тост не вызывается | Улучшение UX: при первой неудаче показывать тост с `data.message` или «Не удалось отправить» (сейчас тост только при нажатии «Повторить») |

### Важно: проверка членства в чате на сервере

- **POST /api/chats/:chatId/messages** (server/messages/routes.ts) **не проверяет**, что пользователь является участником чата. Сообщение создаётся для любого валидного `chatId`. С точки зрения «сообщения не отправляются» это не причина отказа, но это дыра в безопасности: стоит добавить проверку `getChatMemberIds(chatId).includes(userId)` и при отсутствии возвращать 403.

## 3. Профили других участников просмотреть невозможно

### Цепочка на клиенте

- **Страница профиля:** `client/src/pages/UserProfile.tsx`. Параметр `id` из роута `/profile/:id` (или `id/:id`).
- **Для чужого профиля:** загрузка через `fetchProfilePage(id, 50)` → `GET /api/users/profile/${id}/page` (профиль + посты + сториз).
- **Переход из чата:** в `ChatDetail.tsx` кнопка в шапке: `setLocation(\`/profile/${chat.otherMember.id}\`)` — передаётся **uuid** пользователя. Сервер принимает и uuid, и publicId (число в строке).

### Возможные причины (полный список)

| № | Причина | Где проявляется | Как проверить / исправить |
|---|--------|------------------|----------------------------|
| 1 | **401 Unauthorized** | Все запросы к `/api/users/profile/:id` и `.../page` защищены `requireAuth` | Та же диагностика, что и для чатов: куки, Bearer, CORS, сессия |
| 2 | **404 — "Пользователь не найден"** | Сервер возвращает 404 | На сервере: `getUser(idParam)` и при числовом id `getUserByPublicId(parseInt(idParam, 10))`. 404 если пользователя нет, или `target.deletedAt`, или `target.isBlocked`. Проверить в БД: пользователь не удалён, не забанен |
| 3 | **Пустой или неверный id в URL** | При пустом `id` страница редиректит на `/posts` | Убедиться, что ссылки формируются с валидным id (uuid или publicId). Из чата передаётся `chat.otherMember.id` — если `otherMember` null (например, группа или недогруженный чат), кнопка не ведёт в профиль |
| 4 | **Сеть / таймаут** | Запрос не выполняется | Аналогично чатам и сообщениям |
| 5 | **Неверный API_BASE в нативе** | Запрос уходит не на тот хост | Задать `VITE_API_URL` при сборке |
| 6 | **Клиент показывает «ошибку» при 404** | В UserProfile при `fetchProfilePage` возвращается `null` (в т.ч. при 404), ставится `setProfileError(true)` | Ожидаемо: для удалённого/заблокированного пользователя показывается состояние ошибки. Убедиться, что в этом случае есть понятный текст и кнопка «Назад» |
| 7 | **profileVisibility** | В коде есть поле `profileVisibility` (all / followers), но **маршруты GET профиля не ограничивают выдачу** по нему — профиль отдаётся любому авторизованному | Сейчас это не причина «профиль недоступен». Если позже добавить проверку (например, 403 для followers при отсутствии подписки), это станет отдельной причиной |

### Откуда берётся id при переходе из чата

- В шапке чата: `chat.otherMember.id` (uuid). Роут `/profile/:id` принимает и uuid, и числовой publicId — на сервере оба варианта обрабатываются. Использование uuid из `otherMember.id` корректно.

| Область | Авторизация (401) | Сеть / URL / CORS | Сервер (500, БД) | Клиент (логика, UX) |
|--------|--------------------|-------------------|-------------------|----------------------|
| **Чаты** | Нет сессии/токена; куки не уходят в cross-origin; в нативе нет Bearer | Таймаут, нет интернета, неверный VITE_API_URL, CORS | Ошибка в getChatsForUser или цикле; нет/недоступна БД; падение сессии (session save failed) | — |
| **Сообщения** | То же | То же | Ошибка createMessage или уведомлений; БД | user null; пустой chatId; нет тоста при первой ошибке отправки |
| **Профили** | То же | То же | 404: пользователь не найден / удалён / забанен | Пустой id; otherMember null — кнопка не ведёт в профиль |

## Рекомендации по исправлению и профилактике

1. **Единая точка диагностики 401**  
   Проверить один раз: в вебе — кука `ping.sid`, заголовок Cookie в запросе к `/api/chats`; в нативе — наличие `Authorization: Bearer ...` после логина. Убедиться, что при логине в нативе в ответе приходит `token` и вызывается `setUserFromLogin` с ним.

2. **Сервер: проверка членства в чате**  
   В `GET /api/chats/:chatId/messages` и `POST /api/chats/:chatId/messages` добавить проверку: `getChatMemberIds(chatId)`, что `userId` входит в список. При отсутствии — 403. Это устранит возможность чтения/отправки в чужой чат.

3. **Клиент: тост при первой неудачной отправке сообщения**  
   В `useSendMessage` при `!res.ok` (первая отправка) показывать тост с текстом `data.message` или «Не удалось отправить», чтобы пользователь сразу видел причину.

4. **Логирование на сервере**  
   В catch блоках маршрутов `/api/chats`, `/api/chats/:chatId/messages`, `/api/users/profile/:id/page` логировать ошибку (и при необходимости id пользователя/чата без PII), чтобы по логам быстро видеть 500 и исключения БД.

5. **Документировать окружение**  
   В README или deploy-документации явно указать: для нативного приложения обязателен `VITE_API_URL`; для кросс-доменного веба — настройки CORS и SESSION_SAME_SITE (и при необходимости SESSION_SECURE).

6. **Профили: явное сообщение при 404**  
   На странице профиля при `profileError` (в т.ч. 404) показывать текст вида «Пользователь не найден или недоступен» и кнопку «Назад», чтобы не оставлять пользователя без обратной связи.

После внедрения этих шагов основные причины «чаты не загружаются», «сообщения не отправляются» и «профиль просмотреть нельзя» будут либо устранены, либо однозначно видны в логах и в UI.
