# PING MOOT — архитектура мессенджера

## Дизайн-система (UIX)

Интерфейс строится по единой дизайн-системе: **токены → компоненты → паттерны → экраны**. Подробно: **docs/DESIGN_SYSTEM.md**. Токены и утилиты заданы в `client/src/index.css`, типографика и отступы — через классы `.uix-*` и компоненты (PageShell, ListEmptyState, FormError). Все новые и изменённые экраны должны соответствовать чек-листу из DESIGN_SYSTEM.md.

---

## Анализ текущего макета (шаблона)

### Что уже есть в UI
- **Чаты** (`Chats.tsx`): список чатов, папки (Все/Новые/Личное/Работа/…), поиск, контакты.
- **Чат** (`ChatDetail.tsx`): заголовок, сообщения (свои/чужие), эмодзи, ввод, реакции, системные сообщения, групповые чаты.
- **Данные**: всё захардкожено — `FOLDERS`, `CHATS`, `CONTACTS`, `CHAT_DETAILS`, массив сообщений в state.

### Бэкенд
- Express, `routes.ts` пустой, `storage` — только пользователи (MemStorage), схема — только `users`.

### Вывод
Макет задаёт полный UX мессенджера. Чтобы превратить его в работающее приложение с шифрованием, нужно:
1. Заменить моки на реальные API и хранилище.
2. Ввести модульную структуру (одна функция/домен — своя папка, файлы ≤200–300 строк).
3. Добавить слой шифрования (транспорт и/или E2E).

---

## Модульная структура (принципы)

- **1 домен/функция = отдельная папка** (auth, chats, messages, contacts, crypto, ws).
- **1 файл ≈ 200–300 строк** — при переросте разбивать на подмодули.
- **shared** — только типы, схемы, валидация, общие константы; без логики приложения.
- **server** — маршруты, сервисы, хранилище по доменам; общий `index` только подключает модули.

---

## Что делать первым (приоритет)

### 1. Shared: схемы и типы (фундамент)
- Разнести схему по файлам: `users`, `chats`, `messages`, `contacts`.
- Экспорт из `shared/schema/index.ts`.  
Без этого нельзя типизировать API и storage.

### 2. Server: модули и API
- **auth** — регистрация, логин, сессия (уже есть users в storage).
- **chats** — список чатов, создание, папки/метки (по необходимости).
- **messages** — история по чату, отправка.
- **storage** — расширить интерфейс под чаты и сообщения (или вынести в отдельные модули storage).

Сначала: реализовать auth + chats + messages API и подключить к `routes.ts`, чтобы клиент мог уйти от моков.

### 3. Client: переход с моков на API
- Запросы на `/api/auth`, `/api/chats`, `/api/messages`.
- React Query уже есть; добавить хуки/сервисы под новые эндпоинты.

### 4. Real-time (WebSocket)
- Модуль `server/ws` или `server/realtime`: подключение, подписка на чат, доставка новых сообщений, статусы «печатает»/онлайн.

### 5. Шифрование
- Отдельный модуль `shared/crypto` и/или `server/crypto`: протокол (транспорт TLS + опционально E2E), ключи, шифрование тела сообщений. Интеграция после того, как базовый обмен сообщениями уже работает.

## Итоговый порядок работ

| # | Шаг | Результат |
|---|-----|-----------|
| 1 | Shared-схемы (chats, messages, contacts) | Типы и валидация для API и БД |
| 2 | Server: auth + chats + messages (модули, routes, storage) | Работающие API вместо моков |
| 3 | Client: замена моков на API | Реальные чаты и сообщения в UI |
| 4 | WebSocket | Онлайн и доставка сообщений в реальном времени |
| 5 | Crypto | Зашифрованное соединение (и при необходимости E2E) |

Шаги 1 и 2 реализованы: схемы в `shared/schema/`, API auth/chats/messages и storage в `server/`. Дальше: клиент переводится на эти API (шаг 3), затем WebSocket и crypto.

## Профиль, посты, комментарии, реакции, сториз, масштаб

### Что реализовано и работает
- **Страница пользователя**: у каждого пользователя своя страница (`/profile/me`, `/profile/:id`) с аватаром, именем, фамилией, полом, постами из БД.
- **Посты**: таблица `posts`, автор `author_id`, лента и профиль загружают посты через API.
- **Комментарии**: таблица `post_comments`, привязка к `user_id`; API отдаёт имя и аватар автора — комментарии отображаются от имени пользователя.
- **Реакции на постах**: счётчики по эмодзи хранятся в `posts.reactions` (JSONB). Нет API для добавления/снятия реакции — выбор эмодзи на клиенте только в локальном состоянии (после перезагрузки пропадает). Список «кто поставил» не хранится.
- **Сториз**: в UI пока заглушка — один и тот же захардкоженный массив для всех; таблицы и API для сториз нет.

### Масштаб ~200 млн пользователей
Текущая конфигурация: один PostgreSQL, пул с `max: 10` соединений, без PgBouncer, без реплик и партиционирования. Для реальной готовности к такому масштабу нужны: пулер соединений (PgBouncer), индексы (в т.ч. по `author_id`, `post_id`, `created_at`), пагинация везде, кэш (Redis), реплики для чтения; при росте — партиционирование/шардинг.
