# Опережающая дорожная карта: скорость и уверенность UX

Дополняет [`PERFORMANCE_CONFIDENCE_AUDIT.md`](./PERFORMANCE_CONFIDENCE_AUDIT.md): не чеклист «модных технологий», а **ставки на то, что через несколько лет станет базовой планкой** у лучших продуктов (мессенджеры, short video, соцсети), и **поэтапный план**, как к этому прийти без ломки архитектуры за один релиз.

---

## 1. Принцип: опережать не стеком, а инвариантами

| Инвариант | Что это даёт пользователю | Как измерять |
|-----------|---------------------------|--------------|
| **Нулевая «пустая неопределённость»** | Пользователь всегда видит: каркас, кэш, или явную ошибку с действием | Доля экранов без «пустого» промежутка >200 ms при холодном старте |
| **Один источник правды + предсказуемое устаревание** | Нет ощущения «интерфейс соврал» между списком чатов и тредом | События рассинхрона (unread mismatch) в RUM |
| **Восстановление после обрыва за секунды, не минуты** | Доверие как у TG: «сеть пропала — вернулась, всё догналось» | Время от `online` / WS open до консистентного треда (p95) |
| **Стоимость списка сообщений растёт сублинейно** | Длинные чаты и слабые сети не убивают продукт | p95 latency `GET messages`, CPU на presign/N+1 |

Технологии ниже — **средства** закрепить эти инварианты, а не цель сама по себе.

### Как сейчас открывается чат (клиент, UUID)

1. Пользователь тапает строку в списке → опциональный **prefetch** хвоста сообщений (`chatQueryKeys.messagesTail`, см. `docs/CHAT_QUERY_CONTRACT.md`).
2. Роут `/chat/:id` → `ChatDetail` → `useChatMessages(chatIdParam)`.
3. Параллельно (или из офлайн-снимка): `GET /chats/:id`, `GET /chats/:id/folders`, `GET /chats/:id/messages?limit=…` (для групп папки и сообщения частично параллелятся).
4. WebSocket: подписка на тред, догон хвоста после реконнекта; при ошибке — тост (не пустой `catch`).
5. Будущий **bootstrap** (`VITE_CHAT_BOOTSTRAP=1` + `GET …/bootstrap`): один ответ вместо цепочки — включается отдельно, когда контракт стабилен.

## 2. По направлениям: что из «будущего» и зачем

Нумерация сознательно привязана к **пяти этапам аудита** (клиент → API → realtime → медиа → архитектура).

### 2.1 Клиент и воспринимаемая скорость (этап аудита 1)

| Идея «из будущего» | Суть | Конкретика для PING MOOT | Риск внедрения |
|--------------------|------|---------------------------|----------------|
| **Явные машины состояния экрана** | В топ-продуктах редко смешивают «loading» и «показали кэш» молча | Ввести дискретные состояния: `skeleton` / `stale_cached` / `fresh` / `error_retry` для чата и ленты; не новая библиотека обязательно — сначала типы + UI | низкий → средний |
| **Приоритет главного потока (main thread)** | INP станет ещё жёстче; тяжёлые списки = проигрыш | `useTransition` на смену `chatId`, виртуализация треда, мемоизация пузыря, отложенный несущественный рендер | средний |
| **Предсказуемый prefetch** | «Угадывание» следующего экрана по намерению, не по жадности | Prefetch чанка `ChatDetail` при long-press / hover по строке чата; prefetch следующего voice по цепочке; позже — **Speculation Rules** / **link rel=preload** для критичных чанков после логина | низкий |
| **Локальный слой как часть UX, не «офлайн-фича»** | UUID-чаты уже тянут IndexedDB — это зачаток **local-first read path** | Расширить ключи офлайн на все способы входа в чат; единый слой «read from local → reconcile server» | средний |

### 2.2 Сеть, API, сервер (этап аудита 2)

| Идея «из будущего» | Суть | Конкретика для PING MOOT | Риск |
|--------------------|------|---------------------------|------|
| **Проекции вместо N запросов в цикле** | Один round-trip к БД с JOIN / batch-load по id | Заменить N+1 в `enrichMessagesWithReply` на один запрос «все reply_to_id за список»; batch presign или **presign с коротким TTL + кэш в процессе** на время запроса | средний |
| **Агрегированный cold open** | Меньше RTT — главный рычаг на 4G и межконтинентальных линках | Эндпоинт «чат + папки + хвост сообщений» одним ответом (версионировать схему) | высокий |
| **Сжатие и бинарные форматы там, где JSON раздут** | Brotli/gzip на API; при росте — **CBOR/MessagePack** только для внутренних или мобильных клиентов с флагом | `compression` в Node **или** жёстко в nginx; контроль размера полей в ленте/чате | низкий |
| **Граница «тяжёлого» от ядра** | Через 3–5 лет норма — очереди для всего, что >50 ms CPU | Вынести транскод сториз/постers в worker (частично уже есть направление); не блокировать event loop чата | средний |
| **Наблюдаемость как часть контракта** | Без p95/p99 «ускорение» субъективно | SLO на `open_chat`, `list_messages`; логи с `requestId` уже есть — связать с метриками | низкий |

### 2.3 Realtime (этап аудита 3)

| Идея «из будущего» | Суть | Конкретика для PING MOOT | Риск |
|--------------------|------|---------------------------|------|
| **Семантика доставки в UI** | At-least-once + дедуп по id — стандарт для чатов | Формализовать: WS событие ≠ единственный источник; хвост после реконнекта обязателен; дедуп в `setMessages` | средний |
| **WebTransport (когда зрело)** | Мультиплексирование, меньше head-of-line, бинарные кадры | Пилот не раньше стабильной поддержки в целевых WebView; до тех пор — один WS + жёсткий протокол версий | высокий |
| **Явный режим «деградации»** | Пользователь видит: «сообщения могут запаздывать» | Баннер при `outgoingQueue.length > N` или долгом offline; не только тихий refetch | низкий |
| **Изменения с сервера как поток** | Вместо только push в сокет — **лог изменений** для edge-кэшей (долгая игра) | Postgres NOTIFY / outbox таблица / позже consumer на реплике — для инвалидации CDN и read-replicas | высокий |

### 2.4 Медиа: голос, кружки, лента (этап аудита 4)

| Идея «из будущего» | Суть | Конкретика для PING MOOT | Риск |
|--------------------|------|---------------------------|------|
| **Адаптивность даже для короткого видео** | YouTube/IG давно на ABR; кружки вырастут по качеству | Для тяжёлых video_note — эксперимент **LL-HLS/CMAF** + CDN; лёгкие остаются progressive | высокий |
| **Форматы поколения** | AVIF/WebP2 там, где декод не убивает батарею | Постеры кружков и превью ленты — современный стек с fallback | низкий |
| **WebCodecs (выборочно)** | Декод/трим без лишних копий в памяти | Превью первого кадра, клиентский trim до аплоада — только где есть выигрыш и поддержка | средний |
| **Приватный prefetch** | Предзагрузка только **классов данных** с низкой чувствительностью | Не prefetch личных URL в shared cache; presigned — короткий TTL | средний |

### 2.5 Целостность, архитектура, процесс (этап аудита 5)

| Идея «из будущего» | Суть | Конкретика для PING MOOT | Риск |
|--------------------|------|---------------------------|------|
| **Контракты важнее размера PR** | `CHAT_DETAIL_RULES` — правильный прецедент | Любой новый критичный поток — документ + инварианты + кто ломает — тест | низкий |
| **Синтетика + RUM из нескольких регионов** | «У нас быстро в Москве» ≠ продукт | Задержка открытия чата из 2–3 регионов на staging | низкий |
| **Версионирование API и WS** | Старый клиент не должен молчать в битом состоянии | Совместимость 2 версии схемы на переходный период | средний |
| **Опциональный sync-engine (годы)** | Local-first мессенджеры вырастут из ниши | Оценка **PowerSync / Electric / custom outbox+log** только после стабилизации N+1 и агрегатов | очень высокий |

## 3. План реализации волнами (реалистичные горизонты)

Волны **зависимы**: не начинать «sync engine», пока нет стабильного списка сообщений и метрик.

### Волна A — 0–6 недель (фундамент доверия и латентности)

**Цель:** убрать объективно лишнюю задержку и «немые» ошибки.

- Устранить N+1 в reply enrichment; сжатие JSON (middleware/nginx).
- Batch или кэш presign на время одного HTTP-запроса списка сообщений.
- Меньший первый `limit` сообщений + догрузка; skeleton вместо голого `PageFallback` на ключевых роутерах.
- Явный UI фоновой синхронизации списка чатов; убрать тихие `catch` на критичных путях после WS (см. аудит).

**Затронутые зоны:** `server/messages/`, `client/src/lib/queryClient.ts`, `App.tsx`, `Chats.tsx`, `useChatMessages.ts`.

### Волна B — 2–4 месяца (cold open и консистентность)

**Цель:** ощущение «открылся сразу» и одинаковые данные везде.

- Агрегированный cold-open API + клиентский переход с водопада на один запрос (фича-флаг).
- Перевод загрузки сообщений на **единый кэширующий слой** (TanStack Query `useInfiniteQuery` или эквивалент) с политикой stale и инвалидацией из WS/outbox.
- Виртуализация длинного треда; мемо-компонент пузыря.
- Расширение офлайн-снимка на вход по public id / code (где безопасно).

**Затронутые зоны:** `server/chats/`, `useChatMessages.ts`, `ChatDetail.tsx`, `chat-offline-store.ts`, `docs/CHAT_DETAIL_RULES.md`.

### Волна C — 4–9 месяцев (медиа и «как у видеоплатформ»)

**Цель:** кружки и лента не конкурируют за канал и CPU.

- Политика preload видимых и «следующих» медиа; единые ошибки/ retry на плеерах.
- Пилот ABR или отдельный CDN behavior для длинных video_note; метрики до/после.
- Системные `loading="lazy"` / `decoding="async"` для изображений ниже первого экрана.

**Затронутые зоны:** `ChatMessageRow.tsx`, `PostMedia.tsx`, `FeedInlineVideo.tsx`, `server/upload/`, CDN/nginx.

### Волна D — 9–18+ месяцев (опционально, только при метриках и команде)

**Цель:** архитектурный запас на рост DAU и геораспределения.

- Read-replica или материализованные проекции для hot read path (чат/лента).
- Пилот WebTransport **или** выделенный realtime-сервис с чётким протоколом.
- Исследование sync-engine / CRDT для черновиков и офлайн-очереди (не замена Postgres без аудита).

**Затронутые зоны:** инфра, `server/calls/ws.ts`, возможно новый сервис — отдельный ADR.

## 4. Что сознательно не делаем «ради будущего»

- **Полный CRDT для всего треда** без боли конфликтов редактирования — дорого и редко нужно раньше, чем стабильный linear history + WS.
- **Замена PostgreSQL на распределённую БД** ради моды — только если упёрлись в измеримые пределы.
- **Тяжёлый on-device LLM** для prefetch — риск приватности и батареи; до ясных сценариев не ставка.
