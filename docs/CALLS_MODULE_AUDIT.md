# Аудит модуля аудио/видео звонков

Взгляд архитектора фронтенда и бэкенда: что не так сейчас и что улучшить до идеала.

**Актуальный пошаговый план правок (onclose, refs, фабрика peer, error vs status):** [`CALL_REALTIME_IMPROVEMENT_PLAN.md`](./CALL_REALTIME_IMPROVEMENT_PLAN.md).

---

## 1. Обзор архитектуры

| Слой | Компоненты |
|------|------------|
| **Клиент** | `useCall`, `useRealtimeSocket`, `useCallSignaling`, `useWebRtcPeer`, `CallContext`, `CallModal`, `lib/calls`, `lib/incoming-call-alert` |
| **Сигналинг** | WebSocket `/calls` — токен в `Sec-WebSocket-Protocol` (`ping.call.v1` + hex; `?token=` — legacy) |
| **Сервер** | `server/calls/` (token, routes, ws.ts, missed.ts) |
| **Медиа** | WebRTC P2P (simple-peer), только STUN (Google) |

Типичный поток: звонящий получает токен → WS upgrade → `call-initiate` → абонент получает `call-initiate` (и позже `offer`) → принимает → обмен SDP/ICE через WS → peer `connect` → `in-call`.

## 2. Критичные проблемы

### 2.1 Один WebSocket на всё: чаты + звонки

- Один и тот же сокет используется для подписок на чаты (сообщения, typing, voice-recording) и для сигналинга звонков.
- При переподключении WS (сеть, таймаут токена) все подписки восстанавливаются через `sendAllChatSubscriptions`, но активный звонок при этом уже «мертв» (peer разрушен, `endCall` не вызывается по факту обрыва сокета во время звонка).
- Рекомендация: либо явно при `ws.onclose` во время не-idle состояния вызывать `endCall()` (чтобы UI и потоки почистились), либо документировать, что при обрыве WS во время звонка пользователь должен сам завершить звонок (сейчас поведение может быть неочевидным).

### 2.2 Токен одноразовый (consume при upgrade)

- `consumeCallToken` удаляет токен при первом успешном upgrade. Один токен = одно подключение.
- Плюс: безопаснее. Минус: каждое новое подключение (вторая вкладка, переподключение) требует новый POST `/api/calls/token` и новый WS. Текущая логика это учитывает (переподключение по `scheduleReconnectRef` создаёт новый сокет с новым токеном), но при множестве вкладок у одного пользователя будет несколько сокетов — бэкенд это допускает (`socketsByUser` — Set), при приёме звонка другим вкладкам шлётся `call-end`. Это ок, но стоит явно описать в коде/доках.

### 2.3 Таймауты звонка: фронт vs бэкенд

- Бэкенд: `RING_TIMEOUT_MS = 30 * 1000` — через 30 с «нет ответа» → пропущенный звонок, `call-end` обоим.
- Фронт: `RING_TIMEOUT_MS = 60000` — таймер «Абонент не отвечает» через 60 с.
- Итог: обычно звонящий получит `call-end` от сервера на 30-й секунде и завершит звонок по сообщению; 60 с на клиенте — запасной вариант. Лучше вынести оба значения в конфиг/константы и синхронизировать (например, фронт 30 с или 35 с), чтобы не было расхождения в продукте и тестах.

### 2.4 Нет TURN — только STUN

- В коде только STUN (Google). За симметричными NAT и жёсткими файрволами P2P может не подняться.
- Для «идеала» нужен TURN-сервер (coturn и т.п.) и передача его в `iceServers` (и при необходимости конфиг на бэкенде для выдачи TURN-кредов). Без TURN часть пользователей будет получать ошибки ICE/connection.

### 2.5 Удалённое видео через getElementById, не через React

- `remote-video` вешается через `document.getElementById("remote-video")` в `peer.on("stream", ...)` в нескольких местах.
- Работает, пока модалка смонтирована и элемент есть в DOM, но:
  - нет единого источника правды в состоянии (remoteStream не в state/context);
  - при рефакторинге CallModal (условный рендер, портал) элемент может отсутствовать в момент прихода `stream`;
  - сложнее тестировать и переиспользовать логику.
- Рекомендация: хранить `remoteStream` в состоянии (или в ref + setState для перерисовки), передавать в `CallModal` и вешать на `<video>` через `ref`/`srcObject` в эффекте — как для локального потока.

## 3. Архитектурные и UX недостатки

### 3.1 useCall перегружен

- Один хук тянет: состояние звонка, сигналинг WS, создание/уничтожение peer, подписки на чаты (subscribeChat, typing, voice-recording), таймеры, звуки входящего/гудков.
- Сложно тестировать и менять по частям. Идеал: разнести на несколько слоёв, например:
  - `useCallWs` — подключение к `/calls`, отправка/приём сообщений, переподключение;
  - `useCallSignaling` — сценарии call-initiate / accept / reject / end, таймауты звонка;
  - `useCallMedia` — getUserMedia, SimplePeer, local/remote stream, mute;
  - `useCall` — композиция выше + публичный API для UI.

### 3.2 Нет явного «звонок прерван по сети»

- При закрытии WS во время звонка (`ws.onclose`) клиент только обнуляет `wsRef` и планирует переподключение; `endCall()` не вызывается. Пользователь может остаться с «подключение» или «in-call» без реального канала.
- Рекомендация: в `ws.onclose` при `state !== "idle"` вызывать `endCall()` (и при желании показывать тост «Соединение прервано»).

### 3.3 Очистка remote video при завершении

- В `cleanup()` локальный поток снимается и ref обнуляется, но `document.getElementById("remote-video")?.srcObject` не обнуляется. Сейчас модалка при `idle` размонтируется, элемент исчезает — но при возможных будущих сценариях повторного использования того же элемента без размонтирования последний кадр мог бы «залипнуть». Имеет смысл в `cleanup()` явно сбрасывать `srcObject` у remote video.

### 3.4 CallModal: доступность и отклик

- Кнопки без TapScale/хаптик (по правилам проекта — отклик на тап, хаптик на ключевые действия). Стоит обернуть в `TapScaleButton` и при необходимости дать хаптик на «Принять»/«Завершить».
- Для аудиозвонка в in-call показывается имя и заглушка — ок; для видео — один общий блок с `#remote-video`. Переключение камеры (front/back) в UI не предусмотрено — можно оставить как улучшение.

### 3.5 Нет переключения аудио-выхода

- Нет выбора устройства вывода (динамик/наушники/Bluetooth). Для мобильных и десктопа полезно. Требует использования `sinkId` или аналогичного API и выбора устройств через `mediaDevices.enumerateDevices()`.

## 4. Бэкенд

### 4.1 Плюсы

- Разделение: token, routes (REST), ws (сигналинг), missed — понятная структура.
- Пропущенные звонки пишутся в БД и в чат как `missed_call` — консистентно.
- При приёме звонка другим вкладкам того же пользователя шлётся `call-end` — дублирование звонка не остаётся.
- Ожидание офлайн-абонента (CALLER_WAIT_MS) и доставка при подключении (pending call) — хороший UX.

### 4.2 Что улучшить

- Таймауты (RING_TIMEOUT_MS, CALLER_WAIT_MS, PENDING_CALL_TTL_MS) захардкожены в `ws.ts`. Вынести в конфиг (env или config объект).
- Нет метрик/логов по длительности звонков, успешности установки (только логи `[calls] call-initiate`, `forwarding offer/answer`). Для поддержки и аналитики полезно логировать результат (established / rejected / timeout / error).
- Токены в памяти: при рестарте сервера все текущие WS отвалятся. Для горизонтального масштабирования понадобится либо общий store токенов (Redis), либо другой механизм аутентификации WS (например, сессия/кука). Сейчас для одного инстанса — приемлемо.

---

## 5. Безопасность

- Токен одноразовый и с TTL — хорошо.
- Сигналинг идёт только между двумя пользователями (targetUserId проверяется, отправитель берётся из токена). Проверка «есть ли caller/callee в одном чате» не делается — теоретически можно слать call-initiate любому по userId. Имеет смысл на бэкенде при `call-initiate` проверять, что оба пользователя состоят в указанном `chatId` (если звонок привязан к чату).
- WebRTC медиа идёт P2P, сервер не видит трафик — ок.
