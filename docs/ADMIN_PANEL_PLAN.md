# План модуля «Админ-панель» (Admin Panel)

## Аналогия: что видит админ в Telegram

В Telegram (и похожих мессенджерах) платформенный админ обычно имеет доступ к:

1. **Дашборд** — сводка по пользователям, чатам, сообщениям, активности.
2. **Пользователи** — поиск, просмотр профиля, блокировка/разблокировка, удаление аккаунта.
3. **Модерация контента** — жалобы, поиск сообщений, удаление сообщений, блокировка по ключевым словам.
4. **Чаты и группы** — список всех чатов/групп, участники, удаление/ограничение чата, рассылки.
5. **Поддержка** — тикеты/жалобы от пользователей, ответы, закрытие.
6. **Аналитика** — графики регистраций, активности, удержания.
7. **Системные настройки** — флаги функций, лимиты, режим обслуживания, баннеры.
8. **Аудит** — лог действий админов (кто кого забанил, когда).
9. **Роли админов** — список платформенных админов, права (супер-админ, модератор, поддержка).

Ниже — план реализации такого модуля для PING MOOT с разбивкой на подмодули и этапы.

---

## 1. Общая архитектура

- **Отдельное приложение или раздел**: админка как отдельный раздел по пути `/admin/*`, доступный только пользователям с ролью платформенного админа.
- **Бэкенд**: отдельный префикс API `/api/admin/*`, все маршруты защищены проверкой роли.
- **Роли**: ввести в схеме пользователей (или отдельной таблице) поле/связь «роль платформы»: `user`, `moderator`, `admin`, `super_admin`.

## 3. Детализация по подмодулям

### 3.1 Роли и доступ (фундамент)

- **Схема**: добавить в БД поле `platformRole` у пользователя (или таблица `admin_roles`: userId, role, grantedBy, grantedAt).
- **Роли**: `user` | `moderator` | `admin` | `super_admin`.
- **Права**:
  - `moderator`: просмотр пользователей/чатов, бан пользователей, удаление сообщений, просмотр жалоб.
  - `admin`: всё у moderator + управление чатами, рассылки, базовая аналитика, просмотр аудит-лога.
  - `super_admin`: всё + назначение/снятие админов, системные настройки, полный аудит.
- **API**: middleware `requireAdmin`, `requireRole(['admin','super_admin'])` на все `/api/admin/*`.
- **Клиент**: роут `/admin` с проверкой роли; редирект на логин или 403, если не админ.

**Задачи**: миграция БД (platformRole или admin_roles), middleware, страница входа в админку (или вход тем же логином с проверкой роли).

---

### 3.2 Dashboard (дашборд)

- **Метрики на карточках**: всего пользователей, новых за 7/30 дней; всего чатов (ЛС + группы); всего сообщений; активных пользователей за 24ч/7д.
- **График (опционально на первом этапе)**: регистрации по дням за последние 30 дней.
- **Последние действия**: последние N записей из аудит-лога (если уже есть).

**API**: `GET /api/admin/dashboard/stats` — агрегаты из БД.  
**Клиент**: страница `/admin` (или `/admin/dashboard`) с карточками и опционально графиком.

---

### 3.3 Users (пользователи)

- **Список**: таблица (id, publicId, phone, displayName, дата регистрации, статус banned, последняя активность если есть).
- **Поиск**: по phone, displayName, publicId.
- **Фильтры**: по дате регистрации, по статусу (активен/забанен).
- **Действия**: просмотр профиля (в модалке или отдельная страница), «Забанить», «Разбанить», «Удалить аккаунт» (мягкое удаление или полное по политике).

**Схема**: поле `bannedAt` (timestamp) или `isBanned` у пользователя; при необходимости `bannedBy`, `banReason`.  
**API**:  
- `GET /api/admin/users` — список с пагинацией и query-параметрами (search, banned, dateFrom, dateTo).  
- `GET /api/admin/users/:id` — один пользователь (расширенно).  
- `POST /api/admin/users/:id/ban` — бан (body: reason).  
- `POST /api/admin/users/:id/unban` — разбан.  
- `DELETE /api/admin/users/:id` — удаление аккаунта (с проверкой прав).

**Клиент**: страница `/admin/users`, таблица + модалки/страница детализации и действий.

---

### 3.4 Chats (чаты)

- **Список**: таблица (id, тип dm/group, название, кол-во участников, дата создания, последнее сообщение если есть).
- **Поиск**: по названию, по id чата.
- **Фильтры**: тип (ЛС/группа), по дате создания.
- **Детали**: участники, роли в чате, последние сообщения (только для админа).
- **Действия**: удалить чат, «архивировать» (если введём статус), рассылка сообщения по выбранным чатам (осторожно с объёмом).

**API**:  
- `GET /api/admin/chats` — список с пагинацией и фильтрами.  
- `GET /api/admin/chats/:id` — чат + участники + последние сообщения.  
- `DELETE /api/admin/chats/:id` — удаление чата.  
- `POST /api/admin/broadcast` — рассылка (тело сообщения, список chatIds или «все группы» — по политике).

**Клиент**: страница `/admin/chats`, таблица, детализация чата, модалка рассылки.

---

### 3.5 Moderation (модерация контента)

- **Жалобы**: если есть таблица `reports` (reporterId, targetMessageId или targetUserId, reason, status, createdAt), список жалоб с фильтром по статусу.
- **Поиск сообщений**: по тексту (LIKE или полнотекстовый поиск), по chatId, по дате.
- **Действия**: удалить сообщение, удалить сообщение «везде» (если перепосты), забанить отправителя.

**Схема**: таблица `reports` (id, reporterId, targetType: 'message'|'user', targetId, reason, status, createdAt, resolvedBy, resolvedAt).  
**API**:  
- `GET /api/admin/reports` — список жалоб.  
- `PATCH /api/admin/reports/:id` — сменить статус (open/resolved/rejected).  
- `GET /api/admin/messages` — поиск сообщений (query, chatId, dateFrom, dateTo).  
- `DELETE /api/admin/messages/:id` — удаление сообщения.

**Клиент**: страница `/admin/moderation`: вкладки «Жалобы» и «Поиск сообщений», таблицы и действия.

---

### 3.6 Support / Reports (поддержка и тикеты)

- Отдельный тип обращений от пользователей («Написать в поддержку» в приложении).
- **Схема**: таблица `support_tickets` (id, userId, subject, message, status, createdAt, answeredBy, answeredAt, reply).
- **Список тикетов**, ответ на тикет, закрытие.
- **API**: `GET /api/admin/support`, `PATCH /api/admin/support/:id` (ответ, закрытие).  
**Клиент**: страница `/admin/support`.

Можно объединить с «Жалобами» в один раздел «Обращения», если не хочется плодить сущности.

---

### 3.7 Analytics (аналитика)

- **Графики**:  
  - регистрации по дням;  
  - активные пользователи (DAU) по дням;  
  - сообщения по дням;  
  - (опционально) retention.
- **Экспорт**: выгрузка агрегатов в CSV (по желанию).

**API**: `GET /api/admin/analytics/registrations?from=&to=`, `GET /api/admin/analytics/activity?from=&to=`, `GET /api/admin/analytics/messages?from=&to=`.  
**Клиент**: страница `/admin/analytics` с графиками (например Chart.js или Recharts).

---

### 3.8 System (системные настройки)

- **Флаги функций**: например «включить регистрацию», «включить создание групп» — хранить в таблице `settings` (key, value) или в конфиге.
- **Режим обслуживания**: флаг «maintenance» — при true отдавать 503 или показывать страницу «Сайт на обслуживании».
- **Баннер**: текст/HTML баннера для всех пользователей (показывать в шапке приложения).
- **Лимиты**: лимиты запросов (регистрация, логин, отправка сообщений) — настройки для rate-limit.

**API**: `GET /api/admin/settings`, `PATCH /api/admin/settings` (только super_admin).  
**Клиент**: страница `/admin/settings`, форма флагов + баннер + лимиты.

---

### 3.9 Audit log (аудит)

- **Схема**: таблица `admin_audit_log` (id, adminId, action, targetType, targetId, details JSONB, ip, createdAt).
- **Действия**: логировать бан/разбан, удаление пользователя, удаление сообщения, смену ролей, смену настроек.
- **Просмотр**: список с фильтрами по админу, действию, дате.

**API**: `GET /api/admin/audit-log` — список с пагинацией и фильтрами.  
**Клиент**: страница `/admin/audit`.

---

### 3.10 Admins & roles (админы и роли)

- **Список**: пользователи с platformRole !== 'user'.
- **Действия**: назначить роль (moderator/admin), снять роль (вернуть user). Назначение super_admin — только другим super_admin или через миграцию/консоль.
- **Права**: отображать, какие права даёт каждая роль (текстом).

**API**: `GET /api/admin/admins`, `PATCH /api/admin/admins/:id/role` (body: role).  
**Клиент**: страница `/admin/admins`, таблица + модалка смены роли.

---

## 4. План реализации по этапам

### Этап 0 — Фундамент (обязательно первым)

1. Схема: `platformRole` в users или таблица admin_roles; таблица `admin_audit_log`; при необходимости `bannedAt`/`bannedBy` у users.
2. Middleware: проверка сессии + проверка роли на все `/api/admin/*`.
3. Клиент: роут `/admin` с редиректом и layout админки (меню по подмодулям).
4. **Первый супер-админ**: после миграции БД выполнить вручную, например:
   ```sql
   UPDATE users SET platform_role = 'super_admin' WHERE phone = '+79...' LIMIT 1;
   ```
   Либо через seed-скрипт или консоль приложения.

### Этап 1 — Ядро (P0)

1. **Dashboard**: API stats, страница с карточками.
2. **Users**: API список/один/бан/разбан/удаление, страница списка и действий.
3. **Admins & roles**: API список админов + смена роли, страница.
4. Аудит: логирование ключевых действий (бан, смена роли) и вывод в Audit log.

### Этап 2 — Контент и чаты (P1)

1. **Chats**: API и страница списка/детали/удаление; рассылка — по необходимости.
2. **Moderation**: схема reports, API жалоб и поиска сообщений, удаление сообщения; страница.
3. **Analytics**: API агрегатов по дням, страница с графиками.
4. **Audit log**: полный список действий, фильтры, страница `/admin/audit`.

### Этап 3 — Дополнительно (P2)

1. **Support / Reports**: схема тикетов, API и страница (или объединение с Moderation).
2. **System**: таблица/конфиг настроек, API, страница флагов + баннер + maintenance.

## 6. Безопасность

- Все `/api/admin/*` только по сессии и с проверкой роли; не отдавать чувствительные данные (пароли, токены) в ответах.
- Audit log не удалять (или только архивировать); все опасные действия (бан, удаление, смена роли) логировать с adminId и target.
- Rate limit на админ-API, чтобы не брутфорсить админ-сессию.
- При необходимости отдельный логин только для админки (опционально).
