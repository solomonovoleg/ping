# Правила деплоя (обязательны к прочтению перед изменениями)

**Читать перед любым изменением:** `scripts/deploy.sh`, логики `.env` на сервере, `deploy.env`, `scripts/server-setup.sh`.

---

## 1. Источник истины для .env на сервере

- **.env на сервере полностью перезаписывается** при каждом деплое из переменных, собранных при запуске деплоя.
- **`npm run deploy`:** только **deploy.env**.
- **`npm run deploy:test`:** сначала **deploy.env** (секреты и ключи как у прода), затем **deploy.test.env** (тестовая БД, домен `VITE_*`, порты, `VPS_PATH`). Итог = объединение; пустые переопределения в `deploy.test.env` не добавлять (иначе затрут базу).
- Всё, что должно быть на сервере в .env (PORT, SESSION_SECRET, **DATABASE_URL**, S3_*, ADMIN_*, **PINGOK_MICRO_*** и т.д.), после **слияния** должно быть задано. Обычно секреты живут в **deploy.env**; тестовый файл только отличает стенд.
- Полный перечень переменных и напоминание про **`VITE_*` только при сборке** — **`docs/ENV_REFERENCE.md`**. Добавляя новую серверную переменную из кода, допиши **`put ...`** в **`build_server_env`** внутри `scripts/deploy.sh` и строку в справочник.
- **Веб-пуши (FCM в браузере):** в **`deploy.env`** должны быть **`VITE_FIREBASE_*`** и **`VITE_FIREBASE_VAPID_KEY`** (см. **`deploy.env.example`**). Они **не** дублируются в серверном `.env` — только в клиентский бандл при **`npm run build`**. Серверная отправка пушей — отдельно: service account / `FCM_SERVICE_ACCOUNT_B64` и т.д.

## 2. DATABASE_URL

- **Без DATABASE_URL** приложение работает в режиме памяти (MemStorage): пользователи и данные **теряются при рестарте**, войти по старым данным нельзя.
- **Никогда не перезаписывать .env на сервере так, чтобы пропал DATABASE_URL**, если на сервере уже есть БД и приложение ею пользовалось.
- Если в deploy.env нет DATABASE_URL, скрипт деплоя **обязан** попытаться восстановить его (например: сброс пароля пользователя БД на сервере, подстановка в deploy.env и в .env). Не просто писать пустой .env.

## 3. Что нельзя делать

- Менять логику записи .env на сервер без учёта пунктов 1–2.
- Удалять или отключать блок «восстановление DATABASE_URL с сервера» в deploy.sh без замены на другой способ сохранения DATABASE_URL (например обязательное наличие в deploy.env).
- Добавлять в deploy.sh шаги, которые затирают на сервере только часть .env, не документируя это в DEPLOY_RULES.md.

## 4. Сессия (кука) и вход

- **HTTPS:** если сайт открывается по `https://`, в **deploy.env** должна быть **SESSION_SECRET** и **SESSION_SECURE=true**. Иначе кука сессии может не сохраняться в браузере и после входа будет «сессия истекла».
- В production (NODE_ENV=production) кука по умолчанию ставится с флагом `secure`, если не задано `SESSION_SECURE=false`.
- Если фронт и API на разных поддоменах — в deploy.env добавь **SESSION_SAME_SITE=none** (при этом нужен HTTPS и SESSION_SECURE=true).
- **За nginx:** передавай заголовок `X-Forwarded-Proto $scheme`, чтобы приложение считало запрос HTTPS и кука сохранялась (в приложении уже включён `trust proxy`).
- **Мобильный Bearer (JWT в приложении):** подпись считается от `AUTH_TOKEN_SECRET`, иначе от **SESSION_SECRET** (`server/auth/token.ts`). Если при деплое **SESSION_SECRET** на сервере меняется на новый случайный (пустой deploy.env и не подтянулся старый с VPS) — **все выданные токены приложения сразу недействительны**, пользователи увидят вылет на экран входа. Держи **стабильный** `SESSION_SECRET` в `deploy.env` или задай отдельный стабильный `AUTH_TOKEN_SECRET`.

## 5. Проверки перед деплоем (для скриптов и ИИ)

- **`scripts/deploy.sh`** перед `npm run build` проверяет непустые критичные переменные (БД, S3, FCM, OpenRouter, TURN в `VITE_*`, New-Tel при включении). Обход: `DEPLOY_SKIP_ENV_VERIFY=1`; урезанный режим без FCM/OpenRouter/TURN: `DEPLOY_VERIFY_MINIMAL=1` (см. комментарий в `deploy.env.example`).
- Перед изменением deploy.sh: прочитать этот файл и убедиться, что правка не нарушает пункты 1–4.
- После деплоя приложение должно либо использовать DATABASE_URL из deploy.env, либо использовать восстановленный DATABASE_URL (записанный в deploy.env и в .env на сервере).

## 5a. Сжатие ответов API (gzip / brotli)

- **За nginx:** включите сжатие для проксируемых ответов Node (`gzip on;` и при возможности `brotli` в модуле), чтобы тело JSON (`/api/...`) меньше ехало по сети. Проверка: `curl -H "Accept-Encoding: gzip" -I https://ваш-домен/api/chats` — в заголовках должен быть `Content-Encoding: gzip` (или ответ уже сжат на уровне прокси).
- **Прямой доступ к Node без gzip на прокси:** можно задать **`EXPRESS_COMPRESSION=1`** в `.env` на сервере — подключается middleware `compression` в `server/index.ts`. **Не** включать одновременно с nginx gzip до upstream (риск двойного сжатия).
- Личные ответы остаются с `Cache-Control: no-store`; сжатие только уменьшает размер тела, не делает ответ «общим кэшем».

## 5b. Сборка и миграции (не забыть)

- **`npm run deploy`** уже включает **`npm run build`** и на сервере вызывает **`scripts/server-setup.sh`**, который запускает **`scripts/run-migrations.cjs`** (основная БД) и при наличии **`EDGE_DATABASE_URL`** в `.env` на сервере — **`EDGE/db/run-migrations.cjs`**.
- Если выкатываешь код без полного скрипта: не забудь **пересобрать** (`npm run build`) и **прогнать миграции** на сервере вручную (см. `docs/DEPLOY.md`, блок «Сборка и миграции»).

## 6. Микросервис PARSER (ВК)

- В **deploy.env** при включённом парсере должны быть согласованы **`PARSER_SERVICE_SECRET`**, **`PARSER_UPSTREAM_URL`** (на платформе, URL до процесса парсера, обычно `http://127.0.0.1:3093`), при необходимости **`VK_PARSER_TOKEN_KEY`**, **`PARSER_PM2_ENABLED=1`** (см. `ecosystem.config.cjs`).
- **Не публиковать** порт парсера в интернет: по умолчанию слушает **`127.0.0.1`** (`PARSER_BIND`). Не добавлять `proxy_pass` на этот порт в публичный server.
- Внутренний маршрут платформы **`/internal/parser/publish`** не должен быть доступен анонимно с интернета; при проксировании всего сайта на Node имеет смысл в nginx ограничить `/internal/parser` (см. **`PARSER/README.md`**, раздел «Продакшен: сеть и nginx»).

## 7. Постеры видео постов (iSee) и S3

Клиент подставляет URL JPEG в атрибут **`poster`** у `<video>` по прямому публичному URL (как и превью в ленте). Если объект **`.jpg`** в бакете **не доступен для анонимного чтения** (политика бакета / ACL), браузер получит **403**, постер не покажется (при этом само **видео** может открываться по signed URL — симптом: чёрный кадр до декода, хотя воспроизведение есть).

Перед выкатом iSee-постеров на прод проверьте выдачу публичного URL для пары ключей `posts/<id>.jpg` (curl/браузер без куки). См. также **`S3_PUBLIC_ACL`** и справочник **`docs/ENV_REFERENCE.md`** для переменных S3.

**Мониторинг S3:** объём и ошибки бакета (4xx/5xx, латентность, квоты) настраиваются **у провайдера** (CloudWatch для AWS-совместимых API, панель Cloud.ru Evolution Object Storage и т.п.) — не в коде платформы. Локальный каталог **`uploads/`** при включённом S3 может оставаться небольшим: основной объём медиа в объектном хранилище.
