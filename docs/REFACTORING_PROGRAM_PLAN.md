# Рефакторинг-программа (поэтапно и безопасно)

Цель: структуризовать код, снизить риск регрессий при правках, ускорить работу критичных сценариев, привести проект к единым инженерным стандартам.

## Правила выполнения (обязательные)

1. Только маленькие PR (1 зона риска за PR).
2. Сначала тест/контракт, потом структурная правка.
3. Любое потенциально рискованное поведение меняем через временный флаг.
4. После каждого шага: `check` + `build` + ручной smoke по затронутому сценарию.
5. Для крупных файлов: выносить кусками, без изменения внешнего API в первом PR.

## Этап 0. Предохранители и baseline (текущий)

### Цель
- Зафиксировать стартовое состояние.
- Обязать проверки до merge.
- Сформировать безопасный backlog по приоритету риска.

### Шаги
- [x] Сделать backup перед началом программы.
- [x] Снять baseline по крупным файлам (`>500` строк).
- [x] Сформировать пошаговый план и порядок зон.
- [x] Включить PR-check gate для монорепы (`check` + `build`, для `api-hub` + `test`).
- [x] Ввести PR-чеклист риска/проверки/отката (см. `.github/PULL_REQUEST_TEMPLATE.md`).

### Проверка
- CI проходит на PR.
- Есть baseline-документ и список зон по приоритету.

### Критерий готовности
- Нельзя влить PR без минимальных проверок.
- У команды есть единый документ плана и дорожная карта.

### Rollback
- Отмена только инфраструктурных изменений в CI и шаблонах PR.

## Этап 1. Низкорисковое дробление (1-2 недели)

### Область
- Утилиты, парсеры, мапперы, types.
- Без изменения пользовательского поведения.

### Шаги
- [ ] Вынести чистые функции из перегруженных файлов в `model/` или `utils/`.
- [ ] Сохранить прежние импорты через реэкспорт там, где нужно.
- [ ] Добавить unit/contract тест на вынесенную логику.

### Проверка
- `check`, `build`, профильный тест.

### DoD
- -30..50% строк в исходных файлах-целях, поведение без изменений.

### Rollback
- `git revert` PR целиком.

## Этап 2. Серверные границы и storage (2-4 недели)

### Область
- `server/storage/*`, крупные `service.ts`, тонкие `routes.ts`.

### Шаги
- [ ] Разделить storage по доменным секциям.
- [ ] Убрать SQL/инфра-детали из route-файлов.
- [ ] Добавить контрактные тесты на критичные storage-методы.

### Проверка
- `check`, `build`, API smoke на staging.

### DoD
- Снижение связности, меньше точек массовой поломки.

### Rollback
- revert PR; при поведении через флаг — быстрый switch off.

## Этап 3. EDGE (2-3 недели)

### Область
- `EDGE/participant/*`, `EDGE/campaign/*`, `EDGE/tasks/*`.

### Шаги
- [ ] Вынести правила в чистые функции.
- [ ] Оставить в service только оркестрацию.
- [ ] Нарастить тесты на XP/decay/freeze/призы.

### Проверка
- EDGE tests/smoke + проверка API прокси с платформы.

### DoD
- Логика правил прозрачна, легко расширяема.

## Этап 4. api-hub (2-4 недели)

### Область
- `api-hub/src/routes/*`, `api-hub/src/realtime/*`.

### Шаги
- [ ] Сначала HTTP-модули и middleware.
- [ ] Затем realtime/ws с изоляцией событий и ретраев.
- [ ] Добавить регрессионные тесты на multi-tenant изоляцию.

### Проверка
- `npm run test --prefix api-hub` + нагрузочный smoke.

### DoD
- Нет критичных уязвимых зон в fanout/retry.

## Этап 5. Клиент (кроме чата) (3-5 недель)

### Область
- `Posts`, `Board*`, `Settings`, крупные UI-компоненты.

### Шаги
- [ ] Страница -> композиция секций.
- [ ] Эффекты/запросы -> hooks/features.
- [ ] Явные loading/error/empty состояния.

### Проверка
- Smoke по экрану + визуальная регрессия.

### DoD
- Страницы становятся "проводкой", риски правок падают.

## Этап 6. Чат и realtime (в конце, очень осторожно)

### Область
- `ChatDetail`, `useSendMessage`, `useChatMessages`, чатовый realtime.

### Шаги
- [ ] Работать только малыми PR по одному подконтракту.
- [ ] Соблюдать `docs/CHAT_DETAIL_RULES.md`.
- [ ] Никаких смешанных рефакторов (UI+transport в одном PR).

### Проверка
- Расширенный ручной сценарий чата, медиа, reconnect, call-from-chat.

### DoD
- Критичные chat-модули разбиты без регрессий поведения.

## Приоритет работы по крупным файлам

1. Парсеры/утилиты/types (низкий риск)
2. Репозитории и сервисы без смены контракта
3. `server/storage/*`
4. `EDGE/participant/*`
5. `api-hub` HTTP -> WS
6. `Posts`/`Board*`/UI
7. `ChatDetail` и чатовые хуки (последним)

## Метрики успеха

- Количество файлов `>500` строк (цель: устойчивое снижение).
- p95 latency ключевых API без регрессий.
- Error rate 5xx по затронутым маршрутам.
- Размер клиентских тяжёлых чанков.
- Доля откатов PR и инцидентов после релиза.
